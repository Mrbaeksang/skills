# Optimize

속도·메모리·자원·프론트 로딩 비용을 측정하고 개선한다. 단순 코드 정리는 clean, 전체 레포의 개선 후보 발굴은 improve가 맡는다. 입력은 목표 지표·대표 workload·범위·실행 권한이다.

외부 cache·SDK 옵션·실행 환경 차이 또는 자원 누적이 원인 후보이면 [실행 환경 계약](runtime-contract.md)을 읽고 지원 조합·실효 설정·효과를 확인한 뒤 최적화를 정한다. CSS·UI를 수정했다면 전후 측정과 함께 [verify](verify.md)의 해당 화면·조작 검증으로 회귀를 확인한다. 동일 관찰 결과는 재사용한다.

1. [측정 절차](optimize/measurement.md)로 baseline과 profile을 확보한다. 미측정 병목은 가설로 두고 원인을 확정하지 않는다. 성능 예산이 미정이면 임의 목표를 만들지 않는다.
2. CSS·렌더링·bundle·이미지·폰트가 대상이면 [프론트 진단](optimize/frontend.md)을 읽는다. CSS Coverage 한 화면의 결과로 다른 상태의 코드를 삭제하지 않는다.
3. 실제 비용 구간만 최소 변경한다. cache는 무효화·동시성·메모리와 정확성을 함께 검토하며, 구조 변경이 필요할 때만 [architecture](architecture.md)를 사용한다. 분석-only에서는 실행 가능한 개선 항목으로 반환한다.
4. 같은 조건의 전후 분포와 정확성·오류 수를 비교한다. 수정했다면 [test](test.md)로 관련 회귀를 검증한다. 개선이 불명확하거나 다른 지표가 악화됐으면 그 사실을 반환한다. profile 시간과 benchmark 시간은 구분한다.

결과는 baseline·원인 근거·변경·전후 측정·trade-off·미검증 범위다. 측정 결과를 전체 서비스 성능으로 과장하지 않는다.
