# Present

[공통 실행 계약](references/execution-contract.md)을 적용한다. 입력은 주제·원자료 또는 기존 발표자료다. shape/spec/ticket을 선행시키지 않고 이 스킬에서 제작과 검수까지 마친다. 출력은 다른 폴더로 옮겨 직접 열 수 있는 하나의 HTML이다. 최초 원본은 보존하고, 지정된 작업본의 후속 수정은 같은 파일에 이어간다.

먼저 신규 제작·전체 개선·국소 수정을 구분한다. 아래는 신규/전체 작업의 흐름이며, 국소 수정은 관련 원자료와 영향받는 장부터 확인하고 내용·디자인 재설계를 반복하지 않는다. 내용/구도 판단에는 디자인, 원문 공개·가림이나 자산/파일/조작 변경에는 단일 파일 제작, 모션 변경이나 참고 발표의 등장 순서·박자를 재현할 때는 [모션](references/workflows/present/motion.md) 절차를 읽는다. 검수는 항상 변경 영향에 맞게 적용한다. 공통 CSS·폰트·navigation 변경은 영향받는 전체 장/흐름으로 넓히고, 기존 검증은 파일·환경·변경 범위에 여전히 유효한 경우 재사용한다.

제품 사용 과정을 시연하는 장면이 필요할 때만 [제품 시연](references/workflows/present/product-demo.md)을 읽는다. 일반 발표에 제품 데모를 자동 추가하지 않는다.

1. **전달할 의미.** 자료 전체와 기존 발표의 흐름·출처·이미지·발표 노트를 먼저 읽는다. 청중이 무엇을 이해하거나 결정해야 하는지, 발표 시간, 발표용/혼자 읽는 용도, 기존 브랜드를 파악한다. 전체 행사 일정이 원자료라면 요청된 발표자·세션·시간 구간을 먼저 찾고 해당 구간의 요구를 발표 범위로 삼는다. 이미 제공된 정보는 재질문하지 않는다. 결과를 바꿀 미정만 한 번에 묻고 위임된 선택은 진행한다. 새로운 사례·인용은 원출처를 조사하고 확인된 사실과 발표자의 해석을 구별한다. 내용을 보지 않고 CSS부터 바꾸지 않는다.
2. **장면 설계.** [발표 디자인](references/workflows/present/design.md)을 읽고 전체 이야기와 실제 콘텐츠에 맞는 시각 방향을 정한다. 각 장의 핵심 메시지와 가장 적합한 표현을 연결한다. 표지와 가장 어려운 본문 장면으로 방향을 점검한다. 기존 방향이 명확하면 유지하며 매번 시안 선택이나 목차 승인을 요구하지 않는다.
3. **제작.** [단일 파일 제작](references/workflows/present/delivery.md)을 읽고 HTML을 만든다. 사진·일러스트·질감 등 새 비트맵이 설명에 도움이 되면 현재 호스트의 imagegen 스킬/도구를 읽고 사용한다. 실제 화면·인물·근거는 검증된 원본을 사용하고 정확한 글자·수치·도식은 HTML/SVG로 유지한다. 여러 단계의 설명·연출이 필요하면 [모션](references/workflows/present/motion.md)을 읽고 GSAP 등을 사용한다. 외부 스킬 설치나 특정 유료 도구를 필수로 만들지 않는다. 도구가 없으면 기능 축소와 한계를 밝히고 가능한 제작은 계속한다.
4. **보고 고치기.** [발표 검수](references/workflows/present/verify.md)를 실행한다. 전 장을 실제 렌더링해 읽고 내용·위계·줄바꿈·장면 구성·조작 문제를 고친다. 정적 검사나 생성자의 자기평가만으로 아름답다고 판정하지 않는다. 수정 후 영향받는 장과 연속 흐름을 다시 확인한다. 이미지나 모션이 필요 없었던 경우에는 억지로 추가하지 않는다.
5. **전달.** HTML 경로와 짧은 사용법, 실제 확인한 화면/동작, 남은 한계를 알린다. 요청 없는 배포·분석 보고서·디자인 설명 MD를 만들지 않는다. 작업 재개에 필요한 결정만 기존 [작업 기록](references/agent-records.md)에 남긴다. 단일 파일을 만들었다는 사실과 실제 오프라인 검증을 구분한다.
