# UI 검증

## 실행 경계 확보

현재 환경의 도구 목록과 provider inventory에서 browser/native 제어 가능 여부를 확인한다. 노출된 도구의 문서와 해당 앱의 현재 창·탭을 읽고 허용된 테스트 대상을 선택한다. 설치된 브라우저나 자동화 라이브러리가 있다는 사실만으로 제어 가능하다고 간주하지 않는다. 특정 provider, OS, 명령을 필수로 가정하지 않는다.

browser provider가 없으면 사용 가능한 native provider에서 테스트 브라우저를 제어하는 등 허용된 대체 UI 경로를 시도한다. 반대로 native 제어가 없고 브라우저 버전이 수용 기준을 충족하면 그 경계를 검증한다. 서로 다른 앱/플랫폼의 증거는 구분한다. HTTP 요청·DOM 소스·screenshot만 가능한 경우 해당 부분 검증은 남기되 실제 UI 조작은 NOTRUN이다.

테스트 데이터·계정·호스트와 가능한 부수 효과를 확인한다. 로컬 fixture가 유효한 항목과 실제 연동이 필요한 항목을 분리한다. 배포·삭제·결제·권한 변경은 기존 승인 범위 안에서만 실행하며, 부족한 권한을 테스트 성공을 위해 확대하지 않는다. 인증·서비스 접근이 없으면 안전한 로컬 부분을 계속 검증하고 실제 연동은 별도 미검증으로 남긴다.

## 조작과 관찰

화면 조작에서 애플리케이션 밖으로 책임이 넘어가거나 외부 변화가 UI 상태에 영향을 주면 [행동 시나리오](../scenarios.md)로 해당 전이·경계와 검증 조건을 도출한다. 조작 전·진행 중·복귀 후에 사용자가 필요한 행동을 계속할 수 있는지 관찰한다. 외부 변화의 결과만 주입한 검사는 실제 상호작용의 증거와 구분한다.

수용 기준에서 입력과 예상 결과를 정한 뒤 화면의 공개 제어를 사용한다. 현재 화면을 관찰하여 대상을 선택하고, 입력·클릭·키 조작 후 새 상태를 읽는다. 페이지 내부 함수를 직접 호출하거나 기대 결과를 주입하는 것은 사용자 흐름 검증이 아니다.

관련 흐름을 하나씩 확인한다:

- 정상: 실제 입력과 제출 후 사용자에게 보이는 결과 또는 상태 전이를 확인한다.
- 실패: 잘못된 입력 또는 허용된 장애 조건에서 오류 표시, 기존 결과/데이터 보존 여부를 확인한다.
- 복구·회귀: 실패 후 수정·재시도와 인접 기존 흐름을 실행한다. 반복 요청이나 경계값이 관련되면 함께 확인한다.

각 관찰에 대상 화면, 입력/행동, 예상 결과, 실제 결과와 증거 위치를 남긴다. screenshot은 레이아웃 근거이며 조작 이력과 상태 관찰을 대신하지 않는다. 테스트 프로세스 성공과 실제 화면 결과는 별도 행으로 기록한다.

시각적 레이아웃·스타일을 수정한 경우에는 실제 렌더링에서 기존 브랜드/디자인 기준과 **주요 정보의 우선순위, 콘텐츠 밀도, 가독성, 잘림, 상호작용 구분**을 함께 살핀다. 관련 화면 크기·theme·긴 한국어·상태를 선택하고, 가능하면 같은 조건의 변경 전후 결과를 비교한다. 화면 캡처는 시각 비교의 증거일 뿐 클릭·키보드 동작 검증을 대체하지 않는다. 스타일 선호만으로 FAIL을 확정하지 않고 명시된 요구·사용성 영향과 연결한다. 렌더링이 불가능하면 시각 실행 항목은 NOTRUN으로 구분한다.

## 상태와 보고

[완료 증거 형식](evidence.md)에 실행한 앱·provider·버전(미노출이면 미확인), 수용 기준별 PASS/FAIL/NOTRUN, 미실행 환경을 기록한다.

| 관찰 | 다음 행동과 상태 |
|---|---|
| 필수 UI 흐름과 다른 완료 조건이 모두 충족 | 증거 범위에 한해 done |
| UI에서 재현 가능한 결함 | 수정과 같은 흐름 재검증을 계속하며 active |
| 대체 provider로 동일 기준을 검증 가능 | 대체 경로를 실행하며 active; 성공 후 해당 범위만 PASS |
| 도구·인증·서비스·권한 부재로 필수 흐름 실행 불가 | 가능한 부분 검증 후 blocked, 필수 흐름 NOTRUN, 차단 원인과 구체적 재개 조건 |

필수 runtime이 남으면 자동 검사 통과만으로 done으로 바꾸지 않는다. `사용자가 테스트하면 완료`라는 검수 대기를 만들지 않는다. 재개 조건은 필요한 provider 연결, 테스트 서비스 복구, 허용된 테스트 계정 등 실행 가능한 조건으로 적는다. 최종 보고는 결과/상태, 실제 수행한 검증, 남은 문제 순으로 짧게 작성한다.
