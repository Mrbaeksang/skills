# 맥락 기반 시각 품질

UI의 구조·배치·타이포그래피·색·아이콘 등 **시각적 설계·구현·변경 또는 해당 명세·변경의 검토가 포함될 때** 읽는다. 검토에서는 아래 기준으로 근거 있는 finding을 보고하며 수정 단계를 실행하지 않는다. 문구만 수정하거나 기능·성능만 다루는 작업에는 추가 디자인 절차를 강제하지 않는다.

목표는 'AI가 만든 티'를 지우는 것이 아니라 **사용자가 필요한 정보를 찾고 행동할 수 있는, 제품 맥락에 맞는 UI**다. 기존 브랜드·디자인 시스템·명시된 요구가 우선이다. 보라색, 그라데이션, 카드, 이모지, 둥근 모서리를 일괄 금지하지 않는다.

## 1. 기준선부터 파악

- 사용자·기기·핵심 과제, 화면에서 **먼저 읽어야 할 정보**와 **먼저 할 행동**, 실제 콘텐츠 양과 길이를 확인한다.
- 관련 화면, 브랜드 색·서체·spacing/radius 토큰, 기존 컴포넌트를 찾는다. 기존 제품의 시각 언어를 유행에 맞춰 임의 교체하지 않는다.
- 새 제품에 디자인 시스템이 없다면 목적과 콘텐츠 밀도에 맞는 일관된 최소 규칙을 선택한다. 임의의 그라데이션·카드 템플릿을 기본값으로 채우지 않는다.
- 이미지·수치·사용자 후기 등 실제 자료가 없으면 꾸며내지 않는다. 한국어 긴 문장·작은 화면에서의 줄바꿈을 고려한다.

## 2. 다음 결정에 필요한 절차

아래 조건이 성립하면 해당 본문을 읽고 결과를 현재 설계·구현·검토에 반영한다. 아직 정하지 않은 표현을 “일관되게”라는 말로 넘기지 않는다. 기존 결정이 유효하면 재사용한다.

| 결정/문제 | 읽을 절차 | 가져올 결과 |
|---|---|---|
| 새 화면의 방향 또는 구조·표현 재설계 | [디자인 방향](../design.md) | 사용자 과제와 표현 선택의 연결, 중요한 미정 |
| 배치·밀도·반응형 | [구조](../design/structure.md) | 읽기/조작 순서, 그룹과 좁은 화면의 우선순위 |
| 글자 위계·줄바꿈·색의 역할 | [타입과 색](../design/type-color.md) | 기존 토큰에 맞춘 역할, 실제 콘텐츠/대비 확인 |
| 상태 피드백·모션·표면·아이콘 | [상호작용](../design/interaction.md) | 조작을 보존하는 상태별 표현과 전환 검증 |

디자인 선택을 비교할 필요성은 디자인 방향 절차에서 판단한다. 문구만 바꿀 때 이 표 전체를 실행하지 않는다.

## 3. 상투적 패턴은 '탐지 신호'로만 사용

| 후보 신호 | 먼저 확인할 질문 | 근거 없을 때의 개선 |
|---|---|---|
| 제품과 무관한 보라/파랑 그라데이션 | 브랜드/상태 구분에 필요한가? | 기존 브랜드색과 정보 위계에 맞춘다 |
| 모든 카드·버튼이 두껍게 둥글고 그림자가 큼 | 계층·클릭 가능성·그룹 구분에 기여하는가? | radius·elevation 차이를 의미에 맞게 줄인다 |
| 장식 목적의 아이콘·이모지를 제목/본문마다 반복 | 정보를 더 빨리 이해하게 하는가? 브랜드 톤과 맞는가? | 텍스트나 검증된 아이콘으로 단순화한다 |
| 뒤로·복사·공유·새로고침·닫기·삭제 같은 일반 행동이 밑줄 문장이나 큰 글자 버튼 | 대상 플랫폼 사용자가 익숙한 형태인가? 행동이 여러 개 쌓여 내용을 밀어내는가? | 접근성 이름을 단 관례 아이콘으로 바꾸고 한 줄로 모은다 |
| HOT·NEW·영어 소제목·숫자 배지가 남발됨 | 실제 데이터·상태·우선순위를 나타내는가? | 근거 없는 배지는 제거하고 실제 데이터만 표시한다 |
| '새로운 연결의 시작' 같은 추상적 헤드라인 | 이 화면에서 무엇을 할 수 있는지 알려 주는가? | 실제 기능과 다음 행동을 설명한다 |
| 내용마다 동일한 카드 격자·여백·애니메이션 | 비교, 목록 탐색, 데이터 밀도에 적합한가? | 목록/표/구역 등 콘텐츠에 맞는 구조를 고른다 |

단일 신호는 결함의 증거가 아니다. 보라색이 브랜드 색이거나 이모지가 실제 서비스 정체성이면 **유지할 이유**가 있다. 반대로 AI 기본값처럼 보여도 사용성이 더 좋다는 근거가 있으면 유지한다.

## 4. 최소 변경과 검증

1. 문제를 '시각 취향'이 아닌 **구체적인 과제 저해**(중요 정보가 묻힘, 조작 불명확, 스캔 어려움, 브랜드 불일치 등)와 연결한다.
2. 요구 범위 안에서 최소 변경한다. 디자인 시스템 토큰·기존 컴포넌트·실제 동작을 보존하며 새 라이브러리·아이콘·애니메이션을 이유 없이 늘리지 않는다.
3. 새로 강조한 카드·배지·장식에 의미를 설명할 수 없으면 제거·축소를 검토한다. 기능별로 디자인 이유를 장황하게 문서화하지 않는다.
4. 실제 렌더링이 가능한 경우 대표 모바일·데스크톱, 긴 한국어, 주요 상태와 focus에서 정보 위계·가독성·잘림·조작을 확인한다. 가능한 경우 변경 전 화면과 같은 조건으로 비교한다.
5. 렌더링 도구나 비교 기준이 없으면 실행한 범위만 보고한다. 선호·미적 판단을 객관적 PASS/FAIL로 포장하거나 단순 스타일 차이만으로 완료를 막지 않는다.

짧게 **AS-IS 문제 → TO-BE 선택과 이유 → 보존한 브랜드·동작 → 실제 검증/미검증**을 정리한다. 작은 수정에 형식적인 보고서나 새 디자인 시스템을 만들지 않는다.
