# 병합·배포·사용자 화면은 다르다

변경이 저장소에 들어간 것, 운영에 배포된 것, 사용자가 실제로 받는 것은 서로 다른 사건이다. 사용자가 언제 무엇을 해야 변경을 보는지 확인하기 전에는 "반영됐다"고 말하지 않는다.

## 신호

- "반영됐다", "바로 보인다", "배포됐다"고 말하려 한다.
- 변경이 빌드·배포 파이프라인·CDN과 브라우저 캐시·앱에 고정된 번들·스토어 심사·기능 스위치·스키마 마이그레이션·작업 큐·발송 일정 중 하나를 거친다.
- 사용자가 "왜 안 바뀌었지"라고 묻는다.

## 확인할 질문

1. 변경이 사용자에게 닿는 경로를 단계별로 쓰면 무엇인가.
2. 각 단계는 언제 일어나는가: 자동·수동·주기·심사·사용자 행동(재시작, 새로고침, 업데이트).
3. 사용자 쪽에 저장본·캐시·고정 버전이 있는가. 언제, 무엇으로 갱신되는가. 실제 코드나 설정에서 확인했는가.
4. 단계 사이에 서로 맞아야 하는 것이 있는가: 스키마와 바이너리, 서버와 이미 설치된 클라이언트, 스위치와 배포 순서.

## 수행

- 확인 가능한 마지막 단계에서 관찰한다: 운영 응답·배포 기록·실제 기기 화면.
- 옛 클라이언트·옛 번들이 새 서버와 함께 동작하는지 확인한다.
- 경로에 사람의 행동이 필요하면 무엇을 언제 해야 하는지 함께 알린다.

## 보고

- 단계별로 확인함/미확인을 나누고, 미확인 단계는 "언제·무엇을 하면 보이는지"를 쓴다.

## 예

- 웹: 병합 → 배포 → CDN 캐시 만료 → 브라우저 새로고침.
- 모바일: 병합 → 빌드 → 심사 → 사용자 업데이트 → 앱이 내려받아 둔 웹 번들 교체 시점.
- 데이터: 마이그레이션 적용 → 새 바이너리 배포 → 스위치 켜기 → 기존 행 백필.
