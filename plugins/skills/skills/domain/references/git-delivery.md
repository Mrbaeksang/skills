# 커밋과 PR로 변경 전달

커밋·PR·릴리스 설명을 실제로 작성하거나 갱신할 때 읽는다. 코드 변경마다 자동으로 PR을 만들거나 별도 보고서를 추가하는 절차가 아니다. 공통 실행 계약의 사용자 언어를 제목·본문·섹션명에도 적용한다.

## 먼저 확인할 것

현재 branch와 diff, staged 파일, 관련 이슈·결정, 실제 검증 결과, 저장소의 CONTRIBUTING·PR template·최근 커밋 관례를 읽는다. 무관한 변경을 섞지 않는다. 설명은 작업 도중의 계획이 아니라 최종 diff를 기준으로 쓴다. 공개 범위와 기존 승인을 확인하되 이미 허용된 작업을 다시 확인받지 않는다.

## 커밋

- 하나의 설명 가능한 변경 단위로 묶는다. 서로 독립적인 수정은 분리하고, 같은 동작에 필요한 코드·테스트·설정은 함께 둔다. 커밋 수를 채우기 위한 분할은 하지 않는다.
- 제목은 대상과 바뀐 동작이 드러나는 짧은 한 줄이다. `수정`, `개선`, `작업 완료`만 쓰거나 파일명을 나열하지 않는다. 예: `재시도된 결제 이벤트의 중복 적립 방지`.
- 본문은 제목으로 설명되지 않는 원인·선택 이유·호환 영향이 있을 때만 쓴다. 코드에서 바로 보이는 변경 나열, 대화 기록, 에이전트 작업 일지는 생략한다. 작은 수정에 빈 섹션을 붙이지 않는다.
- Conventional Commits는 저장소가 요구할 때 적용한다. `fix:`, scope, issue ID, trailer는 규약대로 유지하고 자연어 설명은 해당 언어로 쓴다. 도구가 요구하는 제목 제한을 지키되 의미를 훼손하는 자의적 길이 규칙은 만들지 않는다.
- commit 전에 staged diff를 읽고 비밀값·임시 scratch·무관한 파일이 없는지 확인한다. 기존 작성자 identity를 사용하며 저자·서명·검증을 꾸며내지 않는다. 승인 없는 amend/rebase/force push로 공개 이력을 다시 쓰지 않는다.

## 여러 단계를 하나로 쌓을 때

사용자가 여러 이슈·단계를 한 branch나 연속 PR로 쌓아 한 번에 병합하기로 했으면 단계마다 커밋을 나누고 이슈를 연결한다. 단계마다는 [변경 영향 범위](lenses/change-impact.md)의 빠른 검사만 돌리고, 브라우저·실제 DB·기기 빌드처럼 무거운 묶음은 스택 끝에서 한 번 돌린다. 실패하면 원인 단계의 커밋을 찾아 그 단계에서 고치고 영향받은 뒤 단계만 다시 확인한다. 배포 순서가 필요한 단계(받는 쪽을 먼저 너그럽게 고친 뒤 값을 바꾸는 경우 등)는 PR 본문에 병합·배포 순서를 적는다.

## PR

처음 보는 사람이 문제와 결과를 이해할 수 있게 첫 문장에 변경 전 문제와 변경 후 동작을 쓴다. 제목도 같은 범위를 표현한다. 기존 template가 있으면 따르되 적용되지 않는 장황한 설명은 추가하지 않는다.

템플릿이 없을 때 필요한 정보는 다음이면 충분하다. 작은 PR은 한두 문단과 검증 한 줄로 합쳐도 된다.

- **변경 이유와 결과:** 어떤 입력/상황에서 무엇이 달라지는지. 파일 목록 대신 사용자나 소비자에게 생기는 결과.
- **검증:** 실제 실행한 명령·시나리오와 결과. 수정 전 재현과 수정 후 결과가 있으면 연결한다. 관련 미실행 경계는 이유를 밝히고, 실행하지 않은 검사에 체크 표시나 PASS를 붙이지 않는다.
- **영향과 이행:** 실제 호환성·설정·데이터 이행·배포 순서·남은 위험이 있을 때만. 사소한 변경에 형식적인 위험 표를 만들지 않는다.

화면이 바뀌면 실제 화면 증거가 유용하고, 흐름이 복잡하면 작은 diff·그림·표를 사용한다. 모든 PR에 다이어그램·스크린샷·HTML을 강제하지 않는다. 이슈·결정·코드 링크는 이유를 보충하며 본문 전체를 대신하지 않는다. 자동 종료 키워드는 해당 이슈의 완료 조건을 실제 충족하고 종료가 범위에 있을 때만 사용한다.

범위가 바뀌면 제목·본문을 최종 구현에 맞게 다시 쓴다. 폐기한 계획, 도구 호출 나열, 과장된 성과, 다른 스킬 모음 소개를 넣지 않는다. 리뷰 지적을 수정했다면 영향받는 검증을 다시 수행하고 현재 head에 해당하는 증거를 쓴다.

## 게시와 이후 상태

PR 생성·업데이트·push·병합·release는 각각 허용된 범위에서만 수행한다. 기존 PR이 있으면 같은 branch와 대상을 확인해 갱신하고 중복 생성하지 않는다. 다중 행 본문은 구조화된 인자나 UTF-8 body-file로 전달하고 실제 게시된 제목·본문·base/head를 readback한다. 응답이 모호하면 조회로 상태를 확인하며 create를 무작정 반복하지 않는다.

필수 검증이 미완료면 ready/병합 완료로 보고하지 않는다. CI·review·merge·release·설치를 구분해 현재 결과와 링크만 짧게 알린다. 릴리스 노트도 같은 언어로 사용자에게 달라진 점·필요한 이행·관련 한계만 쓴다. 작업 branch/worktree 정리는 기존 수명주기 계약을 따른다.
