# 실행 가능한 티켓

UI·사용자 문구를 다루는 티켓에는 [품질 기준](references/workflows/polish/ui-copy.md)을 수용 기준으로 연결한다. 명세의 확정 설계·조사 결과는 재사용한다. 빠진 내용이 조회 가능한 기술 사실이면 [research](references/workflows/research.md), 용어·상태·소유권 해석이면 [domain](references/workflows/domain.md), 공통 기반과 소비자 경계면 [architecture](references/workflows/architecture.md)를 읽고 해당 빈칸만 보완한다. 제품 선택이 필요한 미정은 관련 티켓에 질문/차단 사유로 남기되 독립적으로 준비된 티켓은 계속 작성한다. 단순 분해에 설계 전체를 다시 실행하지 않는다.

먼저 [공통 실행 계약](references/execution-contract.md)을 읽는다. 명세, 현재 이슈, 기존 결정과 승인 범위를 읽고 시작한다. 완성된 명세를 재인터뷰하거나 분해안의 반복 승인을 받지 않는다. 게시 요청이 없으면 채팅으로 반환하며, 로컬 저장·인계가 필요할 때만 [작업 기록](references/agent-records.md)을 따른다.

1. 명세의 각 요구사항·수용 기준·시나리오 ID/링크와 검증 환경을 기존 open/closed 이슈에 대응시킨다. 시나리오는 원본을 유지하고 티켓에는 담당 행동과 필요한 조건을 전달한다. 시나리오가 빠진 행동 요구만 [행동 시나리오](references/workflows/scenarios.md)로 보완한다. 이미 구현된 기반과 진행 중인 책임을 재사용한다. 미결정으로 실행 불가능한 부분만 원인과 재개 조건을 분리한다.
2. 사용자 관찰 결과를 끝까지 제공하는 vertical slice로 나눈다. UI/backend/test 층별 티켓으로 분해하지 않는다. 공통 기반은 소비자가 실제 필요한 최소 계약과 검증 경계를 갖는 선행 티켓 하나로 둔다. 독립 기능을 편의상 직렬 연결하지 않는다.
3. 각 이슈에 배경·목표, 범위/제외, 명세 requirement ID, 입력/출력·오류·권한·상태 불변식, 소유 모듈과 공통 계약, 실제 선행 이슈와 그 산출물, 정상/실패/복구 시나리오, 관찰 가능한 수용 기준과 검증 환경을 적는다. 다른 에이전트가 대화 기록 없이 시작할 수 있어야 한다. 미확정 사항은 확정 계약으로 쓰지 않는다.
4. coverage 표를 만들고 모든 요구사항이 적어도 한 티켓과 검증에 연결되는지 확인한다. 공동 coverage는 소유 책임을 구분한다. 중복 구현, 누락된 소비자/오류 경로, 없는 선행 노드, 자기 의존 및 순환을 검사한다. 순환이면 계약 또는 slice 경계를 고친 뒤 게시한다.
5. 티켓 상태 판정·생성·완료·재개 시 [공유 상태 계약](references/tracker-state.md)을 읽는다. tracker 생성·관계·상태 변경 시 [게시 및 상태 절차](references/tracker.md)를 읽고 적용한다. 각 쓰기와 관계를 readback하고 URL을 대응표에 기록한다. 도구가 없으면 실제 게시와 초안을 구분한다.
6. 결과에 티켓 단위, 요구사항 coverage, dependency graph, 현재 실행 가능한 frontier와 blocked 원인/재개 조건을 제시한다. frontier는 범위/계약이 준비되고 미해결 blocker가 없는 open `status:ready` 이슈 집합이다. 진행 중 active는 별도로 표시한다. 선행 완료·재개 뒤에는 직접/간접 영향을 받는 노드를 재조회하여 다시 계산한다.

다른 세션에 전달하는 작업은 현재 계약·실제 경로·검증 명령과 함께 **무엇이 달라지면 어느 부분을 재확인할지**를 짧게 남긴다. 단순 경로 변경을 전체 중단 조건으로 삼지 않는다. 복잡한 작업에는 재사용할 함수·컴포넌트와 기존 테스트 예시, 실행 위치·필요 환경·기대 관찰·기존 실패도 연결한다. 코드 전문을 복제하거나 작은 티켓에 빈 항목을 강제하지 않는다. 미확인 개선 후보는 조사·실험 티켓으로 구분하고, 어떤 결과에서 수정으로 넘어갈지 적는다.

티켓 작성 완료와 구현 완료는 다르다. 작성한 티켓을 `done` 처리하지 않는다. 필요 검증과 실제 도구 사용의 증거를 분리하고, 조회하지 않은 상태는 snapshot 기준이라고 표시한다.
