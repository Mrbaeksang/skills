# Spec

먼저 [공통 실행 계약](references/execution-contract.md)을 읽는다.

기존 결정에서 도메인 계약이 빠졌을 때만 [domain](references/workflows/domain.md), 모듈 경계·공통 책임·재사용 결정이 빠졌을 때만 [architecture](references/workflows/architecture.md), 기술 선택·현재 API·호환 근거가 없을 때만 [research](references/workflows/research.md)를 사용한다. UI·문구 요구에는 [품질 기준](references/workflows/polish/ui-copy.md)을 적용한다. 확정 설계를 다시 수행하지 않고 누락된 결과만 명세에 합친다.

1. 전달된 대화·결정과 요청된 저장 위치를 확인한다. 기존 프로젝트라면 관련 지침과 현재 파일을 읽는다. 이미 답한 사항은 재질문하지 않는다. 제품의 중요한 미결정이 실제로 작성을 막는 경우에만 질문하고, 나머지는 추정 또는 열린 항목으로 명시한다.
2. [명세 작성 계약](references/specification.md)을 읽고 확정 요구와 근거를 합성한다. 입력이 충분하면 shape나 새 인터뷰를 선행 조건으로 삼지 않는다. 명세의 깊이는 구현자가 대화 없이 이어갈 수 있는 수준으로 맞추되, 해당하지 않는 영역은 이유와 함께 제외한다.
3. 요구마다 식별 가능한 수용 기준을 부여하고 실제 입력·관찰 가능한 결과·실패 조건으로 검증 가능하게 만든다. 확정 결정과 에이전트 제안을 구분한다. 환경에서 확인하지 않은 성능·지원·실행 결과를 사실로 쓰지 않는다.
4. 파일을 요청하면 허용된 위치에 작성하고 읽어 확인한다. 저장·인계가 필요하면 [작업 기록](references/agent-records.md)으로 기존 원본과 결정 링크를 재사용한다. tracker 게시·갱신을 요청받았다면 [게시와 reconciliation](references/publishing.md)을 읽고 허용된 대상에서 수행한다. 파일과 tracker를 모두 요청해도 기본은 상세 원본 하나와 링크이며, 두 곳의 전체 본문을 명시적으로 요청한 경우만 복제하고 원본·갱신 범위를 표시한다. 저장 위치나 게시 요청이 없으면 답변으로 명세를 제공한다. 명세 작성 권한을 구현 권한으로 확대하지 않는다.
5. 입력 결정마다 명세 위치와 수용 기준이 연결되는지, 상충된 결정이나 가정이 확정 사실처럼 섞이지 않았는지 점검한다. 파일/tracker 산출물이 있으면 최종 채팅은 링크, 수행한 검증, 미결정/NOTRUN만 간결히 보고하고 상세 본문을 반복하지 않는다. 명세 완료와 제품 구현 완료를 분리한다.

종료 조건: 적용 가능한 요구와 수용 기준이 추적되고 요청된 산출물을 readback했거나, 미완료 게시/미결정의 원인과 재개 조건이 명시되어 있다. 게시 결과가 모호한 상태는 게시 완료가 아니다.
