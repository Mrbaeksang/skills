# 명세 작성 계약

입력 결정과 기존 코드에서 확인한 사실을 먼저 식별한다. 각각 출처를 남기고 **확정**, **추정/제안**, **미정**으로 구분한다. 새로운 제안에 사용자 승인이라는 표현을 붙이지 않는다. 기존 명세 갱신에서는 안정적인 요구/수용 기준 ID를 유지하며 바뀐 결정의 이유를 남긴다.

## 구현자가 알아야 할 계약

다음 영역을 과제에 필요한 깊이로 작성한다. 작은 CLI에 네트워크 API를 발명하는 대신 해당 없음과 이유를 기록한다.

| 영역 | 명세에 남길 내용 |
|---|---|
| 문제와 범위 | 해결할 문제, 목표, 비목표, actors와 각자의 권한 |
| use case | 시작 조건, 입력, 정상 결과, 실패 결과, 복구/재시도, 변경되지 않아야 할 데이터 |
| 도메인 | 용어, 모듈/데이터 소유자, 불변식, 허용·거절되는 상태 전이 |
| 외부 계약 | 데이터 필드·검증·오류 형태, API/CLI 입력과 출력, 호환성과 중복 요청 의미 |
| 공통 책임 | 인증 기반, 설정, 로깅, 외부 접근과 retry 정책의 담당 경계. 도메인 오류의 의미/불변식은 해당 도메인, 공통 handler는 외부 응답 변환과 공통 기록을 담당 |
| 운영 조건 | 규모·성능·보안·관측성·복구·비용 중 관련된 요구. 미확정 수치는 목표를 발명하지 말고 미정으로 보존 |
| 기술과 의존성 | 기존 선택과 근거, 현실적인 대안/유지안과 trade-off, 공통 기반 선행 작업. 새 버전/지원 사실이 필요하면 공식 출처·조사 날짜·호환 조건을 확인하고, 미확인은 미확인으로 표기 |
| 검증 | 요구 ID → 수용 기준 ID → 실제 입력/관찰 결과/검증 환경. 정상·실패·경계·복구·권한 시나리오 중 관련된 것을 포함 |

공통 오류 설계에는 오류 코드/분류, 외부 노출 정보, 추적 정보, retry 가능성을 연결한다. 공통 handler가 도메인 정책을 결정하거나 모든 로직을 global utility에 모으는 설계를 만들지 않는다. DDD modular monolith를 출발점으로 고려하되 기존 구조와 과제 크기를 존중한다.

## 추적과 완료

- 각 확정 결정이 적어도 하나의 요구 또는 명시적인 비목표에 반영됐는지 대조한다. 각 구현 요구에는 관찰 가능한 수용 기준을 연결한다.
- 예: `R-03 → AC-07: 다른 사용자의 예약 취소 요청 → 권한 오류, 예약 상태 유지 → API 통합 검증`. 단순한 “정상 동작”은 수용 기준이 아니다.
- 추정에 의존하는 기준은 조건부로 표시하고 확정 요구와 구분한다. 중요 미정은 영향 받는 요구와 결정 책임/재개 조건을 적는다.
- 세부 설계가 제안이면 그 설계에 의존하는 각 수용 기준도 조건부다. 예를 들어 성공 HTTP status, idempotency 재생 본문의 형태, 실패 key 보관 정책은 입력에 없으면 제안이다. 상위 요구가 확정이라는 이유로 하위 선택을 확정으로 바꾸거나 “확정 결정에서 따라오는 결과”로 포장하지 않는다. 정적 문구·import 금지 검사가 사용자 흐름의 실제 검증을 대체하지 않게 한다.
- 작성한 검증 계획과 실제 실행한 검증 결과를 분리한다. 명세 작성 중 실행하지 않은 제품 검증은 NOTRUN이다.
