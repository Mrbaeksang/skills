# 디자인 방향과 구현 기준

새 화면의 시각 방향을 정하거나 구조·표현을 재설계할 때 읽는다. 기존 방향이 충분하면 유지하고 해당 변경만 다룬다. 문구 치환·동작 수정에 디자인 탐색을 붙이지 않는다.

1. **의도.** 실제 콘텐츠, 가장 중요한 사용자 판단/행동, 사용 빈도, 밀도와 명시된 브랜드 원칙을 확인한다. 현재 구현을 승인된 방향으로 추정하지 않는다. 반복 피드백은 기존 구조나 완료 기준을 다시 볼 근거이지 같은 장식을 반복 조정할 이유가 아니다. “깔끔하게”를 결과로 삼지 말고 무엇을 먼저 알아보고 어떤 행동을 쉽게 할지 한 문장으로 정한다.
2. **표현.** 그 의도를 읽기 순서·그룹/정렬·밀도·타입 위계·색 역할·상태 피드백의 선택으로 연결한다. 기존 토큰/컴포넌트를 우선하고 새 제품이면 최소 일관된 기준을 제안한다. 값이나 유행보다 선택이 사용자 과제에 미치는 영향을 설명한다.
3. **필요한 깊이.** 구조·반응형 판단은 [구조](design/structure.md), 글자·색 체계는 [타입과 색](design/type-color.md), 조작·상태 변화의 표현은 [상호작용](design/interaction.md)을 해당 결정을 내리기 전에 읽는다. 이름만 열거하거나 모든 파일을 일괄 로딩하지 않는다.
4. **미정 해소.** 텍스트 설명만으로 중요한 시각 선택을 판단하기 어려울 때 [대안 비교](design/compare.md)를 적용한다. 명확한 기존 방향에는 시안을 추가하지 않는다. 제품 결정이 필요하면 독립 질문을 묶고, 위임된 선택은 근거를 붙여 진행한다. 지원/API 사실이 선택을 바꾸는데 불명확하면 [research](research.md)로 확인한다. 미적 취향을 기술 사실처럼 조회하지 않는다.
5. **대표 장면과 수용.** 새 화면·구조/시각 재설계는 구현 전에 실제 콘텐츠의 양·길이, 화면 크기와 중요한 상태를 대표 장면으로 고정한다. 그 장면에서 사용자가 식별해야 할 관계·현재 선택·다음 행동을 수용 기준으로 쓴다. 예를 들어 연결 작업면은 입력칸이 존재하는지가 아니라 어떤 원본이 어떤 결과로 이어지고 선택/변경이 어디에 반영되는지 확인한다. 전체 페이지를 같은 카드로 채우거나 색만 바꾼 것을 목표 달성으로 삼지 않는다. 작은 문구 치환에 이 단계를 붙이지 않는다.
6. **전달.** 원래 명세/작업에 의도·선택·사용할 토큰/컴포넌트·대표 장면/수용 기준·미정을 짧게 연결한다. 전면 개선·전수 조사 요청이면 지정 범위의 화면/콘텐츠 종류와 실제 진입·중요 상태를 먼저 대응시키고, 각각 개선·유지와 이유·미탐색을 구분해 같은 원본에 남긴다. 요구 ID가 모두 티켓에 연결됐다는 사실을 제품 전체를 조사했다는 뜻으로 쓰지 않는다. 구현자는 같은 콘텐츠·크기·상태에서 실제 렌더링/조작으로 대조한다. 위임된 디자인 선택은 자율적으로 진행하고 별도 시안 승인 대기를 자동으로 만들지 않는다. 디자인 초안은 실행 검증이 아니며 읽기-only 요청에서는 시안 코드를 만들지 않는다.
