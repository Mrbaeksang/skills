# 기술 비교 절차

1. manifest/lockfile 및 배포 설정에서 실제 버전과 운영 제약을 확인한다. 설치된 버전, 문서 대상 버전, 후보 버전을 혼동하지 않는다.
2. 중요한 선택당 유지안을 포함한 현실적인 후보 2~3개와 결정을 가르는 공식 근거부터 확인한다. 지원/호환성/핵심 기능을 판별할 충분한 근거가 모이면 조사를 끝낸다. 같은 주장의 반복 조회나 비교에 영향 없는 전수 조사를 하지 않는다. 누락 근거가 실제 추천을 바꿀 때만 추가 조회한다. 필요한 라이브러리·프레임워크·SDK·배포 플랫폼마다 공식 문서, release notes, 지원 정책을 조회한다. 조사 날짜, URL, 문서 대상 버전/게시일, 확인한 사실을 남긴다. 검색 결과 요약만으로 지원 상태나 최신 버전을 확정하지 않는다. 출처가 충돌하면 대상 버전과 시점을 비교한다.
3. 현재 구성 유지와 현실적인 대안을 비교한다. 기능 적합성, 호환성, 유지보수/지원 종료, 라이선스, 비용·운영 부담, 보안·복구, vendor 종속성을 관련 범위에서 평가한다. 후보가 하나뿐이면 제약을 밝힌다. 제약 밖 후보는 탈락 이유를 적고 동등한 대안인 것처럼 추천하지 않는다.
4. 추천과 선택이 달라지는 조건을 적는다. 변경 시 코드/API, 데이터 migration, 테스트/교육, 배포·rollback 비용을 분리한다. 금액·성능 개선 수치는 근거가 없으면 추정 또는 미측정으로 남긴다.
5. 결과를 결정 ID, 모듈 계약, 후속 spec 요구, 공통 기반 의존성과 검증으로 연결한다.

간단한 표는 `후보/버전 | 공식 근거·확인일 | 이점 | 비용·제약 | 추천/조건`이면 충분하다. 조사 불가라면 확인 불가한 항목과 이유, 사용한 로컬 근거 및 재개 조건을 기록하고 조건부 비교를 한다. 기억·제공된 문서만으로 현재 최신/지원 여부를 주장하지 않는다. 필요한 도구가 없다는 이유로 이미 알려진 제약 분석까지 중단하지 않는다.
