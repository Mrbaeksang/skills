# Skills

**질문은 묶어서. 기존 코드는 찾아서. 완료는 실제 검증까지.**

Claude Code와 Codex에서 쓰는 개인 개발 워크플로입니다. 평소에는 **8개 작업 스킬**만 골라 쓰고, 에이전트가 필요한 **9개 전문 절차**를 그때 읽습니다. DDD modular monolith를 출발점으로 삼되 프로젝트 규모와 기존 구조에 맞춥니다.

## 왜 만들었나

AI와 개발하면서 같은 설명을 반복하고, 공통 코드를 다시 만들고, 읽지도 않을 보고서를 받는 일이 싫었습니다. 계획을 세웠다면 실제 동작을 확인할 때까지 이어지는 도구가 필요했습니다.

### 테스트는 사용자의 행동에서 시작합니다

AI는 테스트 코드도 쉽게 늘립니다. 함수마다 mock과 assertion을 붙여도 사용자가 주문을 취소하거나 실패한 요청을 재시도할 때 데이터가 깨지면 소용없습니다. 먼저 **누가, 어떤 상태에서, 무엇을 했을 때, 무엇이 달라지고 보존돼야 하는지** 정합니다. 그 계약을 보호하는 가장 작은 테스트를 선택합니다. 순수한 도메인 규칙에는 unit test가, 연결된 흐름에는 통합 테스트가 적합합니다. TDD의 순서나 테스트 개수보다 실제로 잡는 회귀가 중요합니다.

### DDD는 에이전트가 지켜야 할 의미와 경계입니다

같은 용어를 다르게 해석하거나 공통 handler에 도메인 정책까지 넣으면, 코드는 그럴듯해도 제품은 다른 방향으로 갑니다. **용어·데이터 소유권·불변식**을 먼저 맞추는 이유입니다. modular monolith는 그 경계를 한 배포 단위에서 유지하기 위한 출발점입니다. 작은 기능에 계층·서비스·문서를 더 만드는 명분으로 쓰지 않습니다.

### 성공 응답보다 실제 효과를 확인합니다

라이브러리가 옵션을 받아들여도 실행 중인 서버가 지원하지 않거나 환경 설정이 덮어쓸 수 있습니다. 버전과 설정은 선언값과 실제 적용값을 구분하고, **저장·만료·취소·정리 같은 효과가 발생했는지** 확인합니다. 특히 제한 기능이 조용히 실패하면 무엇이 계속 쌓이는지도 봅니다. 확인하지 못한 환경은 통과로 처리하지 않습니다.

### 코드도 기록도 다음 행동에 도움이 돼야 합니다

필요 없는 추상화, 구현을 그대로 따라 쓰는 테스트, 읽지 않을 분석 보고서는 모두 유지보수할 짐입니다. 기존 코드를 찾아 재사용하고, 바뀌어도 지켜야 할 계약을 테스트하고, 다음 작업에 필요한 결정만 연결해 남깁니다. 많이 만드는 것보다 **필요한 동작을 믿을 수 있게 완성하는 것**을 기준으로 삼습니다.

### 이 기준이 작업에 적용되는 방식

| 자주 겪던 문제 | 이 스킬에 넣은 기준 |
|---|---|
| 독립적인 질문을 하나씩 묻고, 결정한 내용을 다시 확인한다 | 질문은 묶고 확정한 결정은 재사용한다. 실행 가능한 범위는 진행한다 |
| 규모·운영 조건을 놓친 채 기술을 고른다 | 관련 제약부터 확인하고 공식 최신 근거로 유지안·대안의 trade-off를 비교한다 |
| 기존 handler·config·SDK client가 있는데 또 만든다 | 실제 등록·호출 경로와 소비자를 추적하고 재사용·확장·신규를 판단한다 |

승인된 일을 반복 확인하지 않는다는 뜻이지, 분석 요청만으로 코드를 고치거나 외부에 게시한다는 뜻은 아닙니다. 명세의 깊이와 검증 근거는 유지하고 중복 절차와 보고를 줄입니다.

답변부터 명세·이슈·커밋·PR까지 사용자 언어를 따릅니다. 저장소가 요구하는 언어·템플릿은 해당 산출물에 적용하고 코드·식별자는 그대로 둡니다. 별도 PR 스킬을 부를 필요 없이, 승인된 커밋·PR 작업에서 변경 이유·결과·실제 검증을 읽기 쉽게 작성합니다.

## 설치

에이전트마다 **native plugin 또는 npx 중 하나**를 선택하세요. 둘 다 설치하면 같은 스킬이 두 번 보일 수 있습니다. 일반 사용자는 Python이나 저장소 빌드가 필요 없습니다.

### Claude Code

```sh
claude plugin marketplace add Mrbaeksang/skills
claude plugin install skills@baeksang-skills --scope user
```

새 세션에서 `/skills:talk`, `/skills:build`처럼 호출합니다. [scope·제거 안내](docs/claude.md)

### Codex

```sh
codex plugin marketplace add Mrbaeksang/skills
codex plugin add skills@baeksang-skills
```

새 세션에서 설치 출처를 확인해 `$talk`, `$build`를 선택합니다. 호스트가 namespace를 표시하면 `$skills:build`처럼 선택할 수 있습니다. [설치·제거 안내](docs/codex.md)

### 다른 에이전트 / 편집 가능한 설치

```sh
npx skills@latest add Mrbaeksang/skills
```

설치 도구가 안내하는 에이전트를 선택합니다. 전역 설치는 `-g`를 추가하세요. 호스트마다 사용 가능한 도구와 실행 환경은 다릅니다.

## 무엇을 부를까

| 지금 할 일 | 스킬 | 예시 |
|---|---|---|
| 막연한 생각 구체화 | `talk` | “이 아이디어에서 먼저 결정할 것부터 같이 보자” |
| 질문·조사로 개발 방향과 기술 스택 결정 | `shape` | “이 제품을 어떤 구조와 스택으로 만들지 같이 정하자” |
| 이미 결정한 내용을 상세 명세로 | `spec` | “지금까지 결정한 걸 정상·실패·복구 기준까지 명세로” |
| 명세를 실행 가능한 이슈로 | `ticket` | “독립 작업과 실제 선행 관계로 나눠” |
| 명세·티켓·충분한 요청 구현 | `build` | “기존 공통 구현을 쓰고 실제 동작 검증까지 해” |
| 구체적인 버그 원인 규명 | `diagnose` | “재시도하면 두 번 저장돼. 재현하고 고쳐” |
| 기존 레포 분석·개선 | `improve` | “파일 처리 흐름과 재사용 가능한 viewer를 추적해. 지금은 분석만” |
| 명세·변경 코드 검토 | `review` | “이 PR의 누락·회귀·검증 약화를 봐. 수정하지 마” |

`talk → shape → spec → ticket → build`를 매번 완주할 필요는 없습니다. 이미 실행할 내용이 충분하면 `build`부터, 버그면 `diagnose`부터 시작합니다.

### shape는 어디까지 하나요?

**질문 → 답변 반영 → 필요한 조사 → 다음 질문**을 반복합니다. 한 묶음에 답했다고 끝내거나 다시 스킬을 부르라고 하지 않습니다. 관련 요구·규모·운영 제약을 파악하면 미정인 프레임워크·저장소·배포 플랫폼·라이브러리·SDK를 공식 자료로 조사하고, 대안과 추천의 trade-off를 설명합니다. 기존 스택이 충분하면 유지하며, 사소한 선택이나 이미 위임한 결정을 반복 승인받지 않습니다.

중요한 제품·기술 결정이 정리되면 근거와 검증 기준을 전달합니다. 답변을 기다리는 것은 완료가 아닙니다. 명세 작성·이슈 게시·구현은 요청한 범위에 따라 이어가며, 사용자가 중단하거나 제품 요구만 논의하라고 하면 그 범위를 따릅니다.

### 필요한 전문 절차만 읽습니다

```text
8개 작업 스킬
├─ 용어·불변식이 불명확       → domain
├─ 경계·공통 책임·재사용      → architecture
├─ 현재 기술·호환 근거 부족   → research
├─ use case 테스트           → test
├─ 실제 실행·상태·복구 확인   → verify
├─ 불필요한 코드 정리        → clean
├─ UI·문구 완성도            → polish
├─ 측정 가능한 병목 개선     → optimize
└─ 의존성 버전과 코드 이행   → upgrade
```

전문 스킬도 직접 호출할 수 있습니다. 부모와 전문 스킬이 같은 절차를 공유하므로 이미 확인한 답과 검증을 반복하지 않습니다. 단독 설치에도 필요한 참조가 포함됩니다. 참조를 읽는 것은 별도 에이전트 생성이나 native 스킬 호출과는 다릅니다.

부모 스킬은 시작·사용자 답변·새 제약마다 다음 행동에 필요한 절차를 선택합니다. 선택한 이유를 짧게 알리고 본문을 읽어 수행한 뒤, 결과를 원래 작업의 결정에 반영합니다. 유효한 기존 결과는 재사용합니다. 기술·플랫폼·디자인 전문성이 더 필요하면 설치된 관련 스킬도 찾아 적용합니다.

사례의 공통 원인, 사용자에게 전달되는 경로, 검증 조건의 대표성, 반복 비용처럼 놓치기 쉬운 관점도 해당 신호가 있을 때만 확인합니다. 이미 다룬 검증은 재사용하고 단순 문구 치환에 전체 절차를 붙이지 않습니다.

폴더 트리 자체가 자동 호출을 실행하는 프로그램은 아닙니다. 실제 로딩·결과 반영과 불필요한 호출 여부는 행동 평가로 확인하며, 파일 연결 검사만으로 자동 실행을 보장하지 않습니다.

개선 진단은 채택할 후보의 근거와 반례에 집중합니다. 확인된 문제는 수정으로, 미확인 가설은 작은 구분 실험으로 넘깁니다. 제외한 판단은 근거가 유지되는 동안 재사용하고 관련 조건이 바뀌면 다시 확인합니다. 다른 세션에 넘길 복잡한 작업에는 실제 코드 경로와 실행 가능한 검증 방법을 연결합니다.

리뷰는 검증 기준 변경과 diff 밖 소비자까지 필요에 따라 추적합니다. `verify`는 요청 수락과 최종 저장 효과를 구분하고, `test`는 실제 보호 계약이 있는 테스트를 함부로 삭제하지 않습니다.

## 사람에게는 답을, 에이전트에게는 이어갈 기록을

**기본 결과는 채팅입니다.** 요청하지 않은 조사 MD·HTML 보고서·완료 영수증 파일을 만들지 않습니다. README, 사용자 안내, 요청한 명세처럼 독자와 목적이 있는 문서는 작성합니다.

“이어서 해”라는 요청에는 먼저 해당 작업의 기록을 찾고, 미완료 요구·허용 범위·검증 상태를 현재 코드와 대조합니다. 새 조건에 필요한 절차만 다시 선택합니다. 다음 행동만 기억하고 나머지 약속을 잊지 않도록 같은 원본에 연결하되, 저장하지 않은 대화나 다른 환경에서 접근할 수 없는 기록까지 자동 복원한다고 보장하지 않습니다.

다음 세션에 잃으면 안 되는 정보가 있을 때만 기록합니다. 기존 이슈·ADR이 있으면 그것이 원본입니다. 없을 때의 작은 시작은 다음과 같습니다. 아래 파일을 전부 생성하는 템플릿은 아닙니다.

```text
.scratch/
├─ viewer-reuse/
│  └─ state.md          # 현재 목표·결정 링크·미정·다음 행동
└─ decisions/
   └─ D-viewer.md       # 여러 작업이 참조할 때만 분리

작업 → 현재 결정 → 이유·코드·공식 근거
               ├─ 대체한 이전 결정
               └─ 영향받는 이슈 → 구현 PR → 검증
```

현재 기록에서 최신 결정을 바로 읽고, 필요할 때만 이전 근거를 따라갑니다. 전체 대화나 과거 기록을 매번 읽지 않습니다. 중요한 결정은 기존 이슈나 공유 가능한 버전 관리 기록에 남기고, 임시 메모를 저장했다고 다른 세션에도 자동 전달됐다고 주장하지 않습니다. 숨김 폴더도 보안 경계는 아닙니다.

여러 작업에 이어지는 결정은 기존 원본을 가리키는 짧은 기억 진입점으로 연결합니다. 프로젝트가 위치를 정하지 않았고 보존할 정보가 있을 때만 `.scratch/project-memory.md`를 사용합니다. 같은 결정을 다시 복제하거나 매번 파일을 만들지 않습니다. 이전 위임은 대상·환경·행위·유효 조건이 맞을 때 재사용하며, 일회성 승인을 다른 작업의 권한으로 넓히지 않습니다.

상세 명세와 티켓은 필요하면 분리합니다. 기존 GitHub 이슈 본문을 로컬에 다시 복제하지 않고 링크로 연결합니다. read-only 요청에서는 `.scratch`도 쓰지 않습니다. [에이전트 기록 규칙](common/agent-records.md)

사용자 행동 검증은 `shape`에서 목적과 사용 조건을 확인하고, `spec`에서 행동별 상태 변화·책임 경계·유지할 계약을 따라 실패와 복구 시나리오를 도출합니다. `ticket`은 원본을 연결하고, `build`는 해당 위험을 실제로 드러낼 수 있는 테스트와 실행 환경을 선택합니다. 과거 버그 목록을 반복 점검하는 대신 현재 기능의 상호작용에서 검증할 대상을 찾으며, 관찰하지 못한 경계는 미검증으로 남깁니다.

화면 디자인은 사용자 과제에서 방향을 정한 뒤 필요한 구조·타입/색·상호작용 절차만 적용합니다. 중요한 시각 선택이 남으면 실제 콘텐츠로 대안을 비교하고 선택된 기준을 구현·검증에 이어 씁니다. 기존 브랜드를 유지하며 작은 문구 변경에 디자인 전체 절차를 붙이지 않습니다.

```sh
claude plugin update skills@baeksang-skills --scope user
```

**Codex**

```sh
codex plugin marketplace upgrade baeksang-skills
codex plugin add skills@baeksang-skills
```

**npx 설치**

```sh
npx skills@latest update
```

업데이트 후 새 세션을 시작하세요. npx update는 같은 도구가 관리하는 다른 스킬도 갱신할 수 있습니다. Claude marketplace 자동 업데이트는 `/plugin`에서 별도로 설정합니다. [변경 내역](CHANGELOG.md)

## 검증과 기여

설치 성공과 모델의 작업 성공은 별개입니다. 패키징 검사와 실제 에이전트 행동 평가를 구분합니다. 최신 변경은 [변경 내역](CHANGELOG.md)과 [릴리스](https://github.com/Mrbaeksang/skills/releases), 과거 평가 사례는 [0.5.0 평가 기록](evals/results/2026-11-06.md)에서 확인할 수 있습니다. 과거 평가가 현재 모든 버전·호스트의 동작을 보장하지는 않습니다.

스킬은 Markdown과 로컬 참조로 구성됩니다. 에이전트의 파일 읽기·shell·browser·tracker 도구를 사용하며, 별도 상주 runtime이나 vendor SDK를 설치하지 않습니다. 유지보수 도구는 Node.js 표준 라이브러리만 사용합니다.
