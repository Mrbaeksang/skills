# Test

입력은 요구/use case, 변경 경계와 기존 테스트다. 테스트 계획 요청은 계획으로, 테스트 구현 요청은 구현·실행까지 수행한다. 제품 기능 구현은 부모 작업에 남긴다.

1. 정상·입력 실패·권한·경계·의존 실패·복구·반복 요청 중 관련 위험을 공개 경계에 연결한다. 이미 검증되는 경로는 재사용하고 coverage 숫자를 채우려고 중복 테스트를 만들지 않는다.
2. 통합 계약은 실제 경계를 검증하고, 순수한 규칙은 작은 단위 테스트로 검증한다. 내부 메서드·파일 배치·구현을 복제한 계산을 기대값으로 삼지 않는다. 외부 mock의 성공은 실제 연동 성공이 아니다.
3. 버그 수정과 비자명한 새 로직은 관련 실패를 먼저 관찰하고 수정 후 통과를 확인한다. 모든 변경에 red-green을 강제하지 않는다. 문구·단순 설정 변경은 기존 검사와 직접 확인으로 충분할 수 있다.
4. 시간·random·환경·데이터를 통제하고 실패가 의도한 원인인지 확인한다. 기존 소비자·실패/복구의 회귀를 위험에 맞춰 선택한다. JSON은 계약이 byte 형식을 요구하지 않으면 파싱한 값과 채널/exit를 검증한다.

결과는 요구별 테스트 경계·관찰된 실패/통과·미검증 항목이다. 테스트 코드 작성과 실행, 실제 API/UI 검증을 구분하고 부모가 완료 여부를 판정할 수 있게 넘긴다.
