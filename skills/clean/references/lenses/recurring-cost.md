# 반복 비용

사용자마다, 주기마다, 요청마다 도는 작업은 한 번의 비용이 작아도 곱해진다. 단가와 빈도를 먼저 세고, 표준 장치로 줄일 수 있는지 본 뒤에 설계한다.

## 신호

- 폴링·주기 동기화·백그라운드 확인을 만들거나 간격을 바꾼다.
- 요청마다 외부 API·AI 모델·결제 확인·DB 조회를 부른다.
- 큰 파일·목록을 반복해서 내려받거나 다시 계산한다.
- 로그·분석 이벤트·알림을 새로 보낸다.

## 확인할 질문

1. 한 번에 드는 것은 무엇인가: 요청 수, 전송 바이트, 계산 시간, 토큰, 외부 과금 단위.
2. 얼마나 자주 일어나는가: 사용자 수 × 사용자당 빈도. 최악의 경우(오래 켜 둠, 실패 후 재시도)는 얼마인가.
3. 표준 장치로 줄일 수 있는가: 조건부 요청(ETag·304), 캐시 정책, 압축, 변경분만 받기, 묶음 처리, 지수 백오프와 흩뿌림, 푸시로 전환.
4. 줄이는 장치가 신뢰·정확성 경계를 바꾸지 않는가. 캐시 검증값은 전송 최적화일 뿐 무결성 판단을 대신하지 않는다.

## 수행

- 바꾸기 전과 후의 요청 수·바이트를 실제로 재거나, 측정이 불가능하면 가정을 밝히고 계산한다.
- 간격·한도는 이름 있는 상수로 두고 이유를 한 줄로 남긴다.
- 실패 시 재시도가 비용을 키우지 않게 한다.

## 보고

- 사용자 1명 기준 시간당 비용과 주요 이벤트 1회 비용을 전후로 비교한다. 측정값과 추정을 구분한다.

## 예

- 앱의 새 버전 확인: 매번 전체 목록을 받기 → 조건부 요청으로 변경이 없으면 본문 0바이트.
- AI 호출: 화면을 열 때마다 생성 → 결과 저장 후 재사용, 다시 생성은 사용자 행동으로만.
