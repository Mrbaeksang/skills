# Test

입력은 요구/use case, 변경 경계와 기존 테스트다. 사용자 행동·상태 전이·환경 의존 요구에는 [행동 시나리오](scenarios.md)를 읽고 원본 ID/이름과 단계별 기대 결과에서 테스트를 도출한다. 테스트 계획 요청은 계획으로, 테스트 구현 요청은 구현·실행까지 수행한다. 제품 기능 구현은 부모 작업에 남긴다.

기대값을 정하기 전에 용어·불변식·상태 전이가 충돌하면 [domain](domain.md)을 읽어 관련 계약과 미정을 구분한다. 테스트 용이성 때문에 제품 규칙을 대신 결정하지 않는다. 확정 계약에는 이 단계를 반복하지 않는다.

테스트 품질 진단 또는 추가·수정·제거되는 테스트의 유지 가치를 검토할 때만 [테스트 가치](test/value.md)를 읽는다. 단순 실행에 전체 suite 감사를 추가하지 않는다.

1. 테스트 목록은 클래스·함수 목록이 아니라 도메인의 actor와 행동에서 시작한다. `시작 상태 → 사용자/시스템 행동 → 관찰할 결과·불변식`을 정하고 정상·입력 실패·권한·경계·의존 실패·복구·반복 요청 중 관련 위험을 연결한다. 변경한 규칙에서 결과를 달리할 입력·상태의 부류를 골라 기존 검사·추가 검사·미검증에 대응시킨다. 주어진 재현 입력 하나로 그 부류 전체를 검증했다고 보지 않으며 모든 조합을 강제하지 않는다. 기대값은 요구와 도메인 계약에서 얻으며 현재 구현의 출력을 그대로 정답으로 복제하지 않는다. 이미 보호되는 경로는 재사용하고 coverage 숫자를 채우려고 중복 테스트를 만들지 않는다.
2. 그 계약을 믿을 수 있게 검증하는 가장 작은 경계를 택한다. 여러 구성요소의 상호작용은 통합/공개 경계로, 순수한 도메인 규칙·상태 전이는 작은 단위 테스트로 검증한다. 모든 것을 E2E로 만들거나 유효한 unit test를 형식만 보고 제거하지 않는다. 내부 메서드 호출 횟수·파일 배치·구현을 복제한 계산을 제품 정확성의 대리 지표로 삼지 않는다. 외부 mock의 성공은 실제 연동 성공이 아니다.
3. 버그 수정과 비자명한 새 로직은 관련 실패를 먼저 관찰하고 수정 후 통과를 확인한다. 모든 변경에 red-green을 강제하지 않는다. 문구·단순 설정 변경은 기존 검사와 직접 확인으로 충분할 수 있다.
4. 시간·random·환경·데이터를 통제하고 실패가 의도한 원인인지 확인한다. 기존 소비자·실패/복구의 회귀를 위험에 맞춰 선택하고, 실행할 묶음은 [변경 영향 범위](../lenses/change-impact.md)로 바뀐 것이 닿는 곳에 맞춘다. JSON은 계약이 byte 형식을 요구하지 않으면 파싱한 값과 채널/exit를 검증한다.

외부 기능·옵션의 버전/설정에 결과가 의존하면 [실행 환경 계약](runtime-contract.md)으로 실제 지원과 효과를 확인한다. 테스트마다 어떤 행동·규칙의 회귀를 막는지 설명할 수 있어야 한다. 테스트 수와 red-green 수행 자체를 완료 성과로 삼지 않는다.

결과에는 변경 규칙에서 골랐던 입력·상태 부류마다 기존/추가 검사와 관찰 결과 또는 미검증 이유를 대응시킨다. 집계·선택·반복의 로직을 바꿨으면 입력이 없는 경우·하나·여러 개에서 초기값과 반복 경로가 보존되는지 확인한다. 계약상 불가능한 부류는 제외하고 기존 검사로 보호되면 재사용한다. 작은 변경은 한두 줄이면 충분하며 별도 표·문서를 강제하지 않는다. 테스트 코드 작성과 실행, 실제 API/UI 검증을 구분하고 부모가 완료 여부를 판정할 수 있게 넘긴다.
