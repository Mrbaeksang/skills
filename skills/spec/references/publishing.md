# 게시와 reconciliation

tracker 게시나 갱신을 요청받은 경우에만 적용한다. 계정의 기술적 쓰기 권한과 사용자의 작업 승인은 별개다. 현재 대화의 승인 범위와 정확한 repository/tracker를 먼저 확인하고, 이미 명확한 승인은 다시 묻지 않는다. 도구를 사용할 수 없으면 명세를 요청된 로컬 위치 또는 답변에 보존하고 게시 차단 원인과 재개 조건을 보고한다.

## 최초 게시와 재호출

1. 대상, 산출물의 안정적인 식별자, 제목, 완성된 본문을 정한다. 기존 issue URL/번호가 있으면 우선 사용한다. 없으면 원본 명세의 지속적인 키를 본문 marker(예: `<!-- spec-key: booking-cancellation -->`)로 남긴다. 재호출 때 같은 키를 사용하고 새 시간값으로 대체하지 않는다.
2. 쓰기 전에 정확한 대상의 기존 open/closed issue를 조회한다. 제목 유사도만으로 덮어쓰지 않는다. 기존 링크/marker/원본 문서와 내용을 대조하고, 목록 pagination을 끝까지 읽거나 범위가 완전함을 확인한다. GitHub REST issues 목록에 섞이는 pull request는 제외한다. 검색 인덱스 지연이나 잘린 목록의 0건은 부재 증거가 아니다.
3. 일치 1건이면 같은 내용은 no-op으로 URL을 반환한다. 갱신 요청이 있고 내용이 다르면 현재 본문을 다시 읽어 무관한 변경을 보존한 뒤 갱신한다. 충돌하는 동시 편집이나 여러 후보는 쓰기를 중단하고 후보와 해결 조건을 남긴다. 완료된 issue를 임의로 재개하거나 구현 ticket으로 바꾸지 않는다.
4. 기존 산출물이 없다는 충분한 조회와 게시 권한이 있으면 한 번 생성한다. 가능한 도구의 구조화된 body 인자나 UTF-8 body-file을 사용해 줄바꿈/Markdown을 보존한다. 제품 명세 게시에 임의의 구현 완료 라벨을 붙이지 않는다. 기존 tracker vocabulary와 공통 상태 계약을 따른다.
5. 응답 URL/번호에서 본문, 대상, marker와 요청한 변경을 다시 읽어 비교한다. 본문이 잘렸거나 내용이 다르면 성공으로 보고하지 않는다. 사용한 대상과 readback 결과를 증거로 남긴다.

## 응답이 모호하거나 실패한 경우

timeout, 연결 종료, 불완전 응답은 서버가 쓰기를 수행하지 않았다는 증거가 아니다. 실패 직후 create/update를 자동 반복하지 않는다.

- 반환된 ID가 있으면 그 ID를 우선 조회한다. 없으면 같은 대상의 목록을 읽고 안정적인 marker와 본문으로 reconcile한다.
- 정확히 1건이 있고 의도한 내용이면 성공으로 회수한다. 동일 요청을 다시 받더라도 기존 URL을 반환한다.
- 1건이지만 내용이 다르면 현재 상태와 요청을 대조하고 충돌을 해결한다. 갱신 결과가 모호할 때도 기존 내용을 재조회한다.
- 여러 건, 조회 오류, 읽기 권한 부족, 불완전 pagination 또는 응답 후 0건이면 **게시 상태 미확정**으로 남긴다. 조회 가능한 시간/권한/증거가 확보될 때까지 추가 쓰기는 멈춘다. 불확실한 0건만으로 재생성하지 않는다.

모호한 create 이후에는 전체 목록을 다시 읽어도 0건이라는 사실만으로 재생성하지 않는다. 지연된 최초 쓰기가 아직 완료될 수 있기 때문이다. 최초 요청이 적용되지 않았고 앞으로도 적용되지 않는다는 별도의 확정 증거 또는 원자적 idempotency 보호가 확보되어야 새 create를 판단할 수 있다. 시간 경과나 반복 조회 횟수 자체는 그 증거가 아니다.

동시 실행의 check-then-create는 원자적 idempotency 보장이 아니다. 같은 명세를 여러 실행자가 게시 중이면 한 실행자에게 쓰기 소유권을 정하거나 tracker의 원자적 중복 방지 기능을 사용한다. 이 절차만으로 exactly-once를 주장하지 않는다.
