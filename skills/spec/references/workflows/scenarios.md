# 사용자 행동 시나리오

사용자 행동·상태 전이·실행 환경에 따라 결과가 달라지는 요구를 정의하거나 구현·검증할 때 읽는다. 기존 시나리오가 충분하면 그대로 소비하고 변경된 부분만 보완한다. 단순 문구 치환에는 별도 시나리오 문서를 만들지 않는다.

## 한 번 정의하고 이어 쓰기

shape는 사용자 목적·핵심 행동·지원 환경을 파악하고, spec은 기존 명세 안에 시나리오를 확정한다. ticket은 원본의 ID/링크와 담당 범위를 전달한다. build에 명세가 없으면 필요한 시나리오만 현재 작업 안에서 정리한다. 후속 단계는 원본을 재작성하거나 기획 단계로 되돌아가지 않는다.

각 시나리오는 `기존 ID 또는 짧은 이름 / actor와 목적 / 시작 상태·환경 / 행동 순서 → 단계별 관찰 결과 / 실패·복구 / 검증 경계`를 갖는다. 마지막 성공 화면뿐 아니라 사용자가 도중에 입력·조회·중단·재개할 수 있는지도 관련 단계에서 확인한다. 기대 결과는 요구에서 도출하며 미정인 제품 정책은 확정하지 않는다.

## 행동에서 위험 도출

요구에 적힌 성공 경로를 출발점으로 실제 구현·계약에서 각 행동의 전후 상태와 결과를 바꾸는 주체를 추적한다. 사용자가 직접 조작하지 않아도 환경·다른 사용자·외부 시스템이 일으키는 변화까지 포함한다. 다음 질문에서 해당하는 위험만 도출한다.

| 행동에서 찾을 것 | 검증할 질문 |
|---|---|
| 상태와 불변식 | 전·중·후에 무엇이 달라지고 무엇은 유지돼야 하는가? 사용자는 도중에도 필요한 행동을 할 수 있는가? |
| 책임이 넘어가는 경계 | 어느 구성요소가 결과를 결정하는가? 요청 수락과 실제 효과가 다른가? 양쪽 상태가 어긋날 수 있는가? |
| 시간·순서·수명 | 지연·중단·중복·재진입·동시 변경이 가능하다면 어떤 결과가 잘못될 수 있는가? |
| 조건과 복구 | 성공을 위해 암묵적으로 가정한 조건이 바뀌거나 일부만 성공하면 무엇을 보존하고 어떻게 계속해야 하는가? |

각 위험은 `관련 행동·근거 → 깨질 수 있는 계약 → 그 결함을 드러낼 조건 → 관찰할 결과`로 연결한다. 불확실한 구현 가정은 조사·작은 실험으로 확인하고 제품 정책이 불명확할 때만 질문한다. 환경 이름이나 과거 버그 목록을 채우는 것으로 이 분석을 대체하지 않는다.

실제 경로에 존재하는 전이·경계, 사용자 영향과 변경 범위에 따라 대표 조건을 선택한다. 같은 실패 원리는 대표 사례로 검증하고 서로 다른 원인은 따로 다룬다. 모든 조합을 전수 검사하거나 근거 없는 실패를 추가하지 않는다. 구현 중 새로운 경계·실패를 발견하면 영향받는 시나리오를 보완한다.

## 검증 경계 선택

구현 전에 시나리오별로 자동 테스트가 보호할 계약과 실제 환경에서 관찰할 동작을 나누고, 필요한 도구·서비스·기기 접근 가능 여부를 확인한다. 접근 불가인 경계는 조기에 드러내고 가능한 구현·검증은 계속한다. 가장 작은 신뢰할 수 있는 테스트 경계를 선택하고 같은 증거를 중복 생산하지 않는다.

테스트 환경이 위험을 일으키는 주체·상태 전이·상호작용을 실제로 실행하는지 확인한다. 에뮬레이션·mock·합성 이벤트가 그 원인을 생략하거나 결과를 미리 주입하면 해당 경계의 증거가 아니다. 격리 테스트는 내부 계약을, 연동·실제 환경 검증은 생략된 경계를 확인한다. 환경이 비슷하다는 이유만으로 성공을 확대하지 않으며 관찰하지 못한 경계는 NOTRUN이다.

## 실행과 추적

build는 동작 단위가 준비될 때마다 해당 시나리오를 실행하고 실패를 고친 뒤 같은 흐름을 재검증한다. 마지막에만 검증하지 않는다. 완료 전에는 변경된 경계와 인접 회귀만 다시 확인한다.

기존 명세/티켓/테스트/결과에서 같은 ID 또는 이름으로 `요구 → 시나리오 → 자동 테스트·실제 검증 → PASS/FAIL/NOTRUN`을 연결한다. 관련된 각 환경·실패·복구 분기의 누락을 확인하며, 자동 테스트 성공으로 미실행 환경을 덮지 않는다. 별도 추적 문서·보고서 생성은 기본값이 아니다.
