# Spec

먼저 [공통 실행 계약](references/execution-contract.md)을 읽는다.

1. 전달된 대화·결정과 요청된 저장 위치를 확인한다. 기존 프로젝트라면 관련 지침과 현재 파일을 읽는다. 이미 답한 사항은 재질문하지 않는다. 제품의 중요한 미결정이 실제로 작성을 막는 경우에만 질문하고, 나머지는 추정 또는 열린 항목으로 명시한다.
2. 확정 요구와 근거를 명세로 합성한다. 작은 과제는 짧게 작성하되 문제·목표/비목표, 사용자, 정상/실패/복구 흐름, 데이터·권한·불변식, 기술 선택, 수용 기준과 검증 방법을 관련 범위에서 포함한다. 해당하지 않는 영역을 억지로 설계하지 않는다. 기존 기술을 보존하고 새로운 의존성이나 구조는 요구 근거가 있을 때만 제안한다.
3. 요구마다 식별 가능한 수용 기준을 부여하고 실제 입력·관찰 가능한 결과·실패 조건으로 검증 가능하게 만든다. 확정 결정과 에이전트 제안을 구분한다. 환경에서 확인하지 않은 성능·지원·실행 결과를 사실로 쓰지 않는다.
4. 사용자가 파일을 요청하면 허용된 위치에 작성하고 읽어 확인한다. 위치를 지정하지 않았으면 명세를 답변으로 제공한다. 기존 파일이 있으면 요청과 충돌하는 변경을 보존하고 필요한 범위만 갱신한다. 명세 작성만 요청되면 구현이나 tracker 게시는 시작하지 않는다.
5. 입력 결정 누락·모순과 수용 기준 연결을 점검한다. 결과, 실제 수행한 문서 검증, 남은 미결정/NOTRUN을 간결히 보고한다. 명세 완료와 제품 구현 완료를 분리한다.

복잡한 기술 비교나 전체 spec 품질 확장은 후속 기능이다. 최소 호출에서도 확정 요구를 빠뜨리거나 임의로 새 결정을 확정하지 않는다.
