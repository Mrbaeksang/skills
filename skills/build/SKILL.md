# Build

먼저 [공통 실행 계약](references/execution-contract.md)을 읽는다. 입력이 파일 명세든 tracker 티켓이든 아래 같은 요구 → use case → 검증 연결을 사용한다. 다른 스킬 설치나 shape/spec/ticket 호출은 선행 조건이 아니다.

1. **현재 상태 확보.** 실제 cwd, 저장소 루트, branch, worktree, 지침, 기존 tracked/untracked 변경, 실행 도구와 버전을 확인한다. 기존 변경의 범위를 기록하고 겹치는 변경은 원본을 보존한다. tracker 입력이면 본문·수용 기준·선행 의존성을 읽고, 접근 불가 시 전달된 파일/본문으로 실행 가능한 부분을 진행한다. 범위나 권한이 실제로 불명확한 부분만 질문한다.
2. **완료 기준 연결.** 입력의 각 요구 ID에 사용자/상황, 실행 경계, 예상 정상·실패 결과, 검증 방법을 연결한다. 빠진 중요 제품 결정과 되돌릴 수 있는 구현 선택을 구분한다. 이전 결정으로 답할 수 있으면 재질문하지 않는다. 관련 공식 문서와 현재 환경에서 API·버전·호환 조건을 확인하고 조사 날짜·출처·제약을 남긴다. 기존 stack 유지가 기본이며 새 의존성은 필요와 비용을 입증한다.
3. **책임 경계 결정.** 관련 도메인 용어, 불변식, 상태 전이, 모듈 소유 데이터와 공개 계약을 식별한다. DDD modular monolith를 기본으로 기존 구조 안에서 필요한 경계만 만든다. 도메인 모듈은 오류 의미를 소유하고 공통 handler는 외부 응답 변환·안전한 기록을 담당한다. 오류 코드, 노출 정보, 추적 정보, 재시도 가능성을 기존 공통 계약에 맞춘다. 작은 변경에 repository layer나 CQRS, 전면 구조 개편을 강제하지 않는다.
4. **동작 단위 구현.** 관련 위험에 맞는 공개 경계에서 의미 있는 실패를 재현하고 최소 구현으로 통과시킨다. 한 use case씩 검증하며 정상·입력 실패·권한·경계·의존 실패·복구/반복 요청 중 해당 항목을 다룬다. 내부 메서드·파일 배치·복제 계산을 기대값으로 삼지 않는다. JSON 계약은 파싱한 값과 채널·exit code를 검증하며 명세가 공백/직렬화 형식을 요구하지 않으면 문자열 전체 일치 테스트를 추가하지 않는다. 문구 수정 같은 저위험 변경은 직접 확인과 기존 검사로 충분할 수 있으며 형식적인 red-green 테스트를 추가하지 않는다. 변경 후 기존 사용자 변경 보존을 확인한다.
5. **실제 사용 경계 검증.** 자동 검사에 더해 수용 기준에 맞는 API 요청, CLI 프로세스, 브라우저 또는 앱 흐름을 허용된 테스트 환경에서 실행한다. CLI는 실제 exit code·stdout/stderr, API는 실제 응답·상태 전이, UI는 렌더링된 조작 결과를 관찰한다. **화면을 변경하거나 UI 수용 기준이 있으면 [UI 검증 절차](references/ui-verification.md)를 읽고 provider 발견부터 정상·실패·회귀 조작과 완료 판정까지 수행한다.** 코드 읽기나 mock 성공은 해당 runtime 증거를 대신하지 않는다. 실행 가능한 검증을 사용자에게 넘기지 않는다. 도구/권한 부재라면 가능한 대체 경로를 확인하고 남은 항목은 NOTRUN, 원인, 구체적 재개 조건으로 남긴다. 검증 권한이 배포·삭제·결제 권한을 추가하지 않는다. 고위험 인증·결제·데이터 변경은 독립 검토가 완료 조건이다.
6. **증거와 상태 정리.** [완료 증거 형식](references/completion-evidence.md)으로 각 요구를 PASS/FAIL/NOTRUN과 연결한다. 고위험 변경은 사용 가능한 `review` 스킬 또는 별도 검토자/독립 세션에 고정 base/head와 명세를 전달하고 검토 결과를 연결한다. 자기 점검은 독립 검토를 대신하지 않는다. 미해결 고위험 finding, 필수 검증 FAIL/NOTRUN, 필요한 독립 검토 미수행이 남으면 done으로 전환하지 않는다. 수정 후 새 head의 관련 경로와 finding 해소를 재검증한다. 코드·자동 검사·실제 실행·독립 검토가 필요한 범위에서 모두 충족됐을 때만 완료로 판단한다. tracker 상태 전환은 공통 실행 계약을 적용하고, tracker가 없으면 같은 상태와 근거를 로컬 보고에 기록한다. 결과, 수행한 검증, 남은 문제를 한국어로 간결히 보고한다.
