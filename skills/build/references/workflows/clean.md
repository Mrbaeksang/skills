# Clean

코드 작성 뒤의 diff 점검 또는 명시적인 코드 정리 요청에 사용한다. 입력은 대상 diff/경로, 보존할 동작과 수정/검토 권한이다. 기본 범위는 변경된 코드와 영향받는 소비자다.

비슷한 코드의 소유권·공개 계약이 달라 합쳐도 되는지 불명확하면 [architecture](architecture.md)를 읽어 경계를 확인한 뒤 결정한다. 명백한 중복·주석 정리에 전체 구조 설계를 붙이지 않는다.

1. 주변 코드와 실제 호출자를 읽고 복제 로직, 단순 전달 wrapper, 미래용 옵션·설정, 코드를 되풀이하는 주석, 타입 오류를 숨기는 any/cast, 예외를 삼키는 fallback을 후보로 찾는다.
2. 각 후보가 실제 계약·framework·호환성에 필요한지 반증한다. 도메인 경계, SDK adapter, 신뢰 경계의 validation, 데이터 손실 방지 오류 처리는 보존한다. 비슷한 구문만으로 공통화를 강제하지 않는다.
3. 수정 권한이 있으면 기존 helper·표준 기능·설치된 의존성으로 가장 작은 읽기 쉬운 변경을 한다. 검토-only라면 근거 있는 후보만 반환한다. 기능 축소·새 의존성·범위 밖 리팩터링을 끼워 넣지 않는다.
4. 직접 수정했다면 변경 위험에 맞춰 [test](test.md)와 [verify](verify.md)의 해당 검증을 수행한다. 부모의 구현 과정에서 점검만 했다면 부모의 예정된 검증에 포함하고 중복 실행하지 않는다.

결과는 정리한 부분·유지한 계약·실제 검증·남은 후보다. 코드 줄 수 감소를 품질 개선 자체로 보고하지 않는다.
