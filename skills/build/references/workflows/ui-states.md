# 현실적인 UI 상태 만들기

레이아웃·상태 표현을 검증해야 하는데 실제 화면에서 경계 데이터나 실패 상태를 안정적으로 만들기 어려울 때 읽는다. 단순 문구 치환이나 이미 재현 가능한 정상 흐름에 별도 상태 도구를 만들지 않는다.

1. **가능한 상태부터.** 렌더링 분기·schema/API·실제 데이터에서 표시 필드, 길이/개수 제한, 선택값, 누락 가능성과 전이 조건을 찾는다. 빈 값·하나·여러 항목·긴 값·지연·부분 실패 중 변경 위험에 해당하는 것을 고른다. 불가능한 값이나 모든 상태의 곱집합으로 결함을 만들지 않는다. 계약이 불명확하면 가정으로 표시한다.
2. **실제 컴포넌트 사용.** 기존 preview·test fixture·props·mock/cache 경계 중 가장 작은 주입점을 사용한다. 같은 스타일·provider·컴포넌트를 렌더링하고 검증용 화면을 별도 구현하지 않는다. 상태를 만들기 위해 제품 로직을 바꾸거나 테스트 전용 제어를 사용자 화면에 노출하지 않는다. 오래 걸리는 상태는 임의의 sleep 대신 응답을 통제할 수 있는 기존 경계에서 유지한다.
3. **주입 확인.** 고른 데이터/오류가 실제 렌더 경로에 도달했는지 먼저 확인한다. 화면에서 정보 관계·대상 구분·줄바꿈·넘침·복구 동작을 관찰한다. 여러 상태가 동시에 가능하면 관련 조합을 선택하고, 반복 입력·취소가 위험이면 진행 중 조작도 확인한다.
4. **증거 경계.** fixture로 확인한 표현과 실제 API·브라우저/OS·외부 서비스의 전이를 구분한다. 결과 상태를 주입했다고 실제 실패·복귀 흐름을 검증한 것은 아니다. 부모 작업에 상태별 관찰과 미실행 경계를 돌려준다. 재사용할 테스트는 기존 관례에 두고 임시 fixture는 소유권을 확인해 정리하며 사용자의 기존 도구는 보존한다.
