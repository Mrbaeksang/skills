# 기존 구현 재사용과 연결 검증

## 수정 전

1. 이번 기능과 유사한 실제 구현과 호출자를 찾는다. 관련 entrypoint → middleware → domain → 저장소/SDK → 응답 경로를 추적한다. 파일명이나 import 존재만으로 사용 중이라고 판단하지 말고 등록·DI·동적 호출도 확인한다. 작은 변경은 관련 경로만 확인하며 전체 레포 진단으로 확대하지 않는다.
2. 해당하는 공통 error handler, 인증, logger, API client, config loader, UI component와 디자인 token을 확인한다. 전역 설정은 선언 → 기본값 → 환경별 override → 실제 소비자 순서로 읽어 우선순위를 파악한다. 비밀값은 출력하지 않는다.
3. 각 관련 책임을 그대로 재사용 / 기존 계약 확장 / 새 구현 필요로 결정한다. 적합한 기존 경로가 있으면 이를 사용하고, 우회하거나 새로 만들 때만 불일치와 이유를 짧게 남긴다. 공통 폴더에 있다는 이유로 부적합한 정책을 재사용하지 않는다. 도메인 의미·권한·데이터 소유권이 다른 유사 코드는 합치지 않는다.

## 구현과 완료 확인

- 새 기능은 등록·호출·설정·실패 처리까지 연결한다. 기존 공통 handler가 있는 경로에 별도 응답 형식이나 중복 예외 변환을 만들지 않는다. handler가 처리할 도메인 오류와 안전한 외부 계약을 맞춘다.
- 공유 코드·기본 설정을 바꾸면 소비자를 검색하고 영향받는 정상·오류 경로를 확인한다. 새 기능만 통과시키고 기존 소비자를 깨뜨리지 않는다. 관련 fixture·exports·설정 예시도 실제 계약에 맞춘다.
- 완료 전 diff와 실제 실행 경로를 대조한다. 미등록 함수·component, 미사용 설정, 중복 retry/logging/validation, 공통 client 우회를 확인한다. 테스트에서만 연결된 경로는 실제 통합 완료가 아니다.
- 관련 공개 경계의 정상·실패 및 기존 소비자 회귀를 검증한다. 정적 연결 확인과 실제 실행 결과를 구분하고 실행하지 못한 경로를 남긴다. 별도 탐색 보고서나 형식적인 체크리스트 파일은 만들지 않는다.
