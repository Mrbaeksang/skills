# 모델 응답 품질

문제가 코드가 아니라 모델 출력의 품질에 있을 때 적용한다. 예를 들면 의도를 잘못 분류함, 형식은 맞지만 내용이 빗나감, 캐릭터·어조가 어긋남, 다음 행동을 건네지 않음 같은 경우다. 예외·잘못된 계산·스키마 파싱 실패처럼 코드가 결정적으로 틀린 경우에는 일반 진단 절차를 쓴다.

1. **평가 세트를 먼저 고정한다.** 수정 전에 다음을 정해서 작업 기록에 남긴다.
   - 입력: 실제 실패 대화와 그 주변 정상 사례, 짧은 답·거절·화제 전환 같은 경계 사례
   - 사례별 판정 기준: 관찰 가능한 조건으로 쓴다. "자연스럽다" 같은 표현은 쓰지 않는다.
   - 실행 조건: 모델·설정·실행 횟수
   후보끼리는 같은 세트로만 비교한다. 세트를 바꾸면 이전 결과와 합치지 않고 새 기준선부터 다시 잰다.
2. **기준선을 잰다.** 현재 구현으로 세트를 여러 번 실행하고 사례별 통과율을 기록한다. 한 번 성공한 것을 PASS로 확정하지 않는다.
3. **고치는 순서.** 출력의 원인과 가까운 곳부터 고친다.
   1. 지시문
   2. 예시
   3. 출력 스키마와 선택지 구성
   4. 모델에 주는 맥락과 도구 노출
   5. 샘플링 설정
   서버 쪽 강제 규칙·상태 기계·사후 보정을 더하려면, 앞 단계로 세트의 실패가 줄지 않았다는 측정 근거가 있어야 한다. 그 근거와 함께 추가한다.
4. **후보를 비교한다.** 한 번에 한 가지만 바꾸고 같은 세트의 통과율을 비교한다. 사례별로 나아진 것과 나빠진 것을 함께 기록한다. 전체 통과율만으로 회귀를 덮지 않는다.
5. **반복 상한을 둔다.** 같은 접근으로 두 후보 연속 개선이 없으면 멈춘다. 원인 가설을 다시 세우고 결과를 사용자에게 보고한다. 실패한 접근에 규칙을 계속 덧붙이지 않는다.
6. **보고.** 기준선과 최종 통과율, 사례별 변화, 바꾼 것, 남은 실패 사례, 실행 조건을 짧게 남긴다. 실서비스 사용자 대화로 확인하지 않은 범위는 NOTRUN으로 구분한다.
