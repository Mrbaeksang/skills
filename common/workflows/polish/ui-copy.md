# UI·문구 품질 기준

현재 작업의 화면·문구에만 적용한다. 기존 브랜드와 명시된 디자인 방향을 우선하며 별도 디자인 절차나 도구 설치를 요구하지 않는다. 화면의 시각적 설계·레이아웃·스타일을 설계·구현·변경하거나 해당 명세·변경을 검토할 때 [맥락 기반 시각 품질 기준](visual-quality.md)을 추가로 읽는다. 검토에서는 기준을 평가에만 적용하고 수정 권한으로 확대하지 않는다. 문구만 수정하는 작업에는 필요하지 않다.

## 설계·명세·티켓

- 화면의 사용자, 핵심 행동, 실제 콘텐츠와 기존 component·용어를 확인한다. 이미 확인된 내용을 다시 묻지 않는다. 랜딩 페이지는 판단과 행동, 업무 화면은 과제 수행, 문서는 이해를 기준으로 구조를 고른다.
- 제품과 무관한 hero, 같은 카드의 반복, 의미 없는 label·숫자 장식, 모든 구역의 등장 효과는 목적이 있을 때만 쓴다. 특정 색·글꼴·카드 자체를 금지하거나 기존 브랜드를 다른 유행으로 바꾸지 않는다.
- 관련 정상·빈 상태·로딩·실패·복구 흐름과 관찰 가능한 수용 기준을 남긴다. 버튼의 결과, 오류 후 입력 보존, 재시도 가능 여부를 실제 계약과 맞춘다. 모든 화면에 모든 상태를 억지로 추가하지 않는다.

## 구현·문구 작성

- 사용자가 할 수 있는 행동을 구체적으로 적고 같은 행동에는 같은 이름을 쓴다. 파일 선택을 여는 버튼은 모호한 '시작하기'보다 '파일 선택'처럼 결과를 알린다. 내부 구현 용어는 사용자 판단에 필요한 경우에만 표시한다.
- 오류는 확인된 원인과 가능한 다음 행동을 설명한다. 서비스 장애를 입력 오류로 표현하거나 보존되지 않은 내용을 저장했다고 안내하지 않는다. 예: 실제 제한을 넘었을 때 '파일이 10MB를 넘습니다. 10MB 이하 파일을 선택하세요.' 제한값은 실제 설정을 따른다.
- 기능·가격·성능 수치·후기·고객 로고를 지어내지 않는다. 미확정 콘텐츠는 작업 중 명시하고 완료된 제품 사실처럼 게시하지 않는다. 의미 없는 홍보 문장은 실제 기능 설명으로 바꾸거나 제거한다.

## 검증·리뷰

- 기존 UI 검증 과정에서 실제 버튼 결과와 안내 문구, 오류·복구 동작, 긴 한국어·좁은 화면의 잘림, 키보드 focus와 접근성을 함께 확인한다. source 검사만으로 렌더링·조작 성공을 주장하지 않는다.
- 오해를 유발하는 문구, 동작 불일치, 근거 없는 주장, 조작 불가를 구체적 결함으로 보고한다. 상투적인 스타일은 맥락에 따른 개선 후보로 구분하고 미적 점수만으로 완료를 막지 않는다. 요청된 검증을 실행할 수 없으면 미검증 범위를 남긴다.
