# booking-v1 티켓 및 상태 변경 계획

`/ticket` 명령은 이 세션에 없어 실행되지 않았고, 일반 요청으로 직접 작성했습니다. 파일 읽기·변경, 서버 호출, 대시보드 보고는 하지 않았습니다. **아래 상태 변경은 모두 사용자가 준 snapshot을 기준으로 한 미실행 계획이며, 전이 결과는 예상값입니다.**

## 1. 사실과 계획 구분

| 구분 | 내용 |
|---|---|
| snapshot에서 확인 | P 존재, F `open,status:active,feature`, C `open,status:blocked,bug`, C→F 의존, C marker 일치 1건, C 본문 완성, 운영자 조회 티켓 없음 |
| 미확인 | tracker 종류, 티켓 번호, C–P 부모 연결, 의존이 native인지, F·P의 본문과 marker, 제품 코드 구조 |
| 계획 | O 생성, 연결 확인, F·C·O 상태 전이 |

C 생성 응답은 timeout 났지만 readback에서 1건이 확인됐으므로 **C는 재생성하지 않습니다.** 동일 본문이므로 본문도 수정하지 않습니다. 다만 timeout으로 후속 연결이 빠졌을 수 있어 C–P 연결은 실행 시 확인합니다.

## 2. 상태 변경 계획

**상태 규칙**
- **라벨:** snapshot에 있는 `status:active`, `status:blocked`만 사용하고 새 status 라벨은 만들지 않습니다. `status:active`는 실행 가능하다는 뜻이며, 실제 실행 증거는 아닙니다.
- **Frontier:** 부모가 아닌 open 티켓 중 모든 blocker가 "완료"로 닫힌 티켓입니다. `not planned`로 닫힌 blocker는 해제 조건이 아닙니다.
- **라벨 변경:** 전체 교체 대신 해당 status 라벨만 추가·삭제해 `bug`, `feature`와 다른 라벨을 보존합니다.

**지금 적용할 단계**

| # | 동작 | 멱등성 처리 |
|---|---|---|
| 1 | 전체 목록을 모든 페이지까지 다시 읽고 marker별 건수 확인 | 읽기 전용 |
| 2 | C–P, C→F 연결 확인 후 빠진 것만 추가 | 이미 있으면 성공으로 처리 |
| 3 | `booking-v1/operator-status`가 0건이면 O를 `status:blocked,feature`로 생성 | 1건이면 생성 생략, 2건 이상이면 중단 후 보고 |
| 4 | O–P 부모 연결과 O→F blocking 연결 | 이미 있으면 성공으로 처리 |
| 5 | O의 본문, 라벨, 연결을 readback | 불일치 시 부족분만 보정 |

O 생성도 timeout 나면 바로 재시도하지 않고 전체 목록을 다시 읽어 판단합니다. 0건일 때만 재생성합니다. 중복이 발견되면 자동으로 닫거나 삭제하지 않습니다.

F·P는 본문을 확인하지 못했으므로 덮어쓰지 않습니다. 실행 시 F 본문이 아래 계약보다 부족하면 부족한 항목만 추가합니다.

## 3. 시점별 상태와 Frontier

P는 전 구간 open이고 라벨은 변경하지 않습니다.

| 시점 | F | C | O | Frontier |
|---|---|---|---|---|
| **F 완료 전** (O 생성 후) | open, `status:active`, `feature` | open, `status:blocked`, `bug` | open, `status:blocked`, `feature` | **{F}** |
| **F 검증 통과·완료 후** | closed, `feature` | open, `status:active`, `bug` | open, `status:active`, `feature` | **{C, O}** |
| **C 구현 중** | closed, `feature` | open, `status:active`, `bug` | open, `status:active`, `feature` | {C, O} (C는 담당 중) |
| **C 검증 중** | closed, `feature` | open, `status:active`, `bug`, 증거 기록 중 | 동일 | {C, O} (C는 담당 중) |
| **C 검증 통과·완료 후** | closed, `feature` | closed, `bug` | open, `status:active`, `feature` | **{O}** |
| **완료 후 C 재개** | 변경 없음 | closed, `bug` 유지 | 변경 없음 | **{O}** (O가 닫혔으면 ∅) |

**전이 순서**
- **F 완료:** 검증 증거 기록 → F `status:active` 제거 후 완료로 닫기 → readback → C·O에서 다른 미완료 blocker가 없는지 확인 → 각각 `status:blocked`를 `status:active`로 교체합니다.
- **F 검증 실패:** F는 open, `status:active`로 남고 C·O는 blocked를 유지합니다.
- **C 검증 실패:** C는 open을 유지하며 닫지 않습니다. 외부 장애로 진행할 수 없을 때만 원인을 기록하고 `status:blocked`로 바꿉니다.

**재개 규칙**

| 재개 시 C 상태 | 동작 |
|---|---|
| 닫힘 + 증거 있음 | no-op (재오픈, 재구현, 중복 댓글, 재생성 모두 없음) |
| 닫힘 + `status:active` 잔존 | 해당 라벨만 제거 |
| open + 완료 증거 있음 | 증거를 확인한 뒤 라벨 제거 후 닫기 |
| open + 증거 없음 | 마지막 검증 지점부터 이어서 작업 |

중간에 끊겨 F는 닫혔는데 C·O가 blocked로 남아 있으면, 재개 시 관계를 다시 계산해 라벨만 보정합니다.

## 4. 관계 표현

| 관계 | native 지원 시 | 미지원 시 대체 |
|---|---|---|
| **부모** | P 아래 F·C·O를 sub-issue로 연결 | 자식 본문에 `Parent: P`, P 본문에 marker 체크리스트 |
| **순서** | F가 C·O를 blocking | 자식 본문에 `Blocked by: booking-v1/foundation` |
| **상태** | status 라벨은 표시용으로 함께 유지 | 라벨로 표시하고, 본문 관계를 파싱해 frontier 계산 |
| **중복 탐지** | marker 검색 후 전체 목록으로 확인 | 전체 페이지를 순회하며 본문의 marker 정확 일치로 확인 |

- Sub-issue는 계층만 나타내며 실행 순서를 보장하지 않으므로, 순서는 blocking으로 별도 표현합니다.
- P는 모든 자식의 부모일 뿐 blocker나 frontier 후보가 아닙니다. F·C·O가 모두 완료되면 닫을 수 있습니다.
- 대체 방식을 쓰면 자동 차단이 되지 않으므로 "native 미지원, 본문 기반 관리"라고 보고합니다.
- native와 본문 관계가 충돌하면 더 보수적인 쪽(차단)을 적용하고 보고합니다.

## 5. 티켓 본문

### 명세 공백에 적용한 기본값

아래는 명세에 없어 티켓 작성 시 정한 값이며, 변경 가능한 가정입니다.

| ID | 기본값 |
|---|---|
| A1 | 예약 시작까지 **정확히 24시간 남은 시점은 허용**하고, 서버 시각 기준으로 판단 |
| A2 | 타인 예약 취소는 존재 노출을 막기 위해 없는 예약과 같은 404로 응답 |
| A3 | HTTP 상태: 401, 403, 404, 409(취소 기한 초과), 503(저장 장애), 500(예상치 못한 오류) |
| A4 | 오류 응답에 `retryable` 필드를 추가해 R4를 표현 |
| A5 | 운영자 조회는 예약 ID 단건 조회로 한정 |

### F: 인증 기반과 공통 API 오류 경계

`ticket-key: booking-v1/foundation` (제안값이며 기존 F의 marker는 확인 필요)
**유지 상태:** `open,status:active,feature` / Parent: P / Blocked by: 없음 / Blocks: C, O

**목표:** C와 O가 재사용할 인증 기반과 공통 오류 변환 경계를 한 번만 제공합니다.

**범위**
1. 인증된 요청에서 사용자 ID와 역할(`member`, `operator`)을 담은 주체 정보를 제공합니다.
2. 인증 필수 처리와 역할 검사 기능을 제공합니다.
3. 도메인이 넘긴 오류(`code`, `safeMessage`, `retryable`, 상태 분류)를 다음 응답으로 변환합니다.
   `{ "code": "...", "message": "...", "traceId": "...", "retryable": false }`
4. 요청마다 trace ID를 부여하고 오류 응답과 서버 로그에 같은 값을 남깁니다.
5. 예상치 못한 예외는 `INTERNAL_ERROR`, 500, `retryable=false`와 일반 문구로 변환합니다.

**제외:** 예약 오류 코드나 규칙, 취소, 조회, 삭제, 환불. 경계는 예약 오류의 의미를 판단하지 않고 변환만 합니다.

**인수 기준**
- [ ] 미인증 요청은 `AUTH_REQUIRED`, 401을 받습니다.
- [ ] 역할이 맞지 않으면 `AUTH_FORBIDDEN`, 403을 받습니다.
- [ ] 테스트용 가짜 도메인 오류의 코드, 메시지, `retryable`이 그대로 변환됩니다.
- [ ] 오류 응답에 스택, SQL, 내부 호스트, 원본 예외 문구가 없습니다.
- [ ] 응답과 로그의 trace ID가 일치합니다.
- [ ] 경계 코드에 예약 전용 코드와 분기가 없습니다.

**검증과 완료:** 저장소의 기존 테스트 명령과 실제 API 실행으로 위 항목을 확인합니다. 실행 명령, 결과, 커밋을 댓글로 남긴 뒤 `status:active`를 제거하고 완료로 닫습니다. C·O의 blocker 해제는 이 증거가 기록된 뒤에만 수행합니다.

### C: 회원 본인 예약 취소

`ticket-key: booking-v1/cancel`
**유지 상태:** `open,status:blocked,bug` / Parent: P / Blocked by: F

> 서버의 C 본문은 snapshot상 완성본이므로 **게시하지 않습니다.** 아래는 실행 계약을 보여 주기 위한 재구성본입니다. 실제 본문을 직접 본 것은 아니므로, 차이가 있으면 덮어쓰지 말고 보고합니다.

**목표:** 회원이 본인 예약을 시작 24시간 전까지 취소할 수 있게 합니다. 이미 취소된 예약의 재요청도 같은 성공으로 처리합니다.

**범위:** 인증된 회원용 취소 API와 예약 도메인의 취소 규칙, 오류 정의를 구현합니다. 인증과 오류 변환은 F를 재사용합니다.

**판정 순서**
1. 인증 확인: 실패 시 `AUTH_REQUIRED`, 401
2. 예약 읽기: 저장 장애 시 `BOOKING_STORAGE_UNAVAILABLE`, 503, `retryable=true`
3. 예약 없음 또는 타인 예약: `BOOKING_NOT_FOUND`, 404
4. 이미 취소됨: **기한과 무관하게** 같은 성공 응답, 쓰기 없음
5. 기한 초과: `BOOKING_CANCEL_WINDOW_CLOSED`, 409
6. 취소 저장: 실패 또는 결과 불명확 시 503, `retryable=true`
7. 성공: 200 `{ "bookingId": "...", "status": "CANCELLED" }`

**제외:** 예약 행 삭제, 환불 처리와 환불 호출, 운영자 조회, 공통 경계 재구현.

**인수 기준**
- [ ] 25시간 전 취소는 성공하고, 저장된 상태가 `CANCELLED`로 바뀝니다.
- [ ] 정확히 24시간 전은 성공하고, 23시간 59분 전은 409이며 상태가 유지됩니다.
- [ ] 첫 취소와 재취소의 상태 코드와 본문이 같고, 재취소 시 쓰기가 없습니다.
- [ ] 기한이 지난 뒤 이미 취소된 예약을 재요청해도 성공합니다.
- [ ] 동시 취소 요청은 모두 성공하고 상태 전이는 1회만 일어납니다.
- [ ] 타인 예약과 없는 예약의 응답이 동일하며, 타인이 이미 취소한 예약도 성공으로 응답하지 않습니다.
- [ ] 읽기·쓰기 장애는 성공 응답 없이 503, `retryable=true`, trace ID를 반환합니다.
- [ ] 장애 복구 후 재시도하면 성공하고 전이는 1회입니다.
- [ ] 취소 후 예약 행이 남아 있고 환불 호출이 없습니다.

**검증과 완료:** 고정 시계와 저장소 장애 주입을 쓴 use case 테스트, 실제 API 실행으로 확인합니다. 명령, 결과, 커밋을 기록한 뒤 `status:active`를 제거하고 완료로 닫으며 `bug`는 유지합니다.

### O: 운영자 예약 상태 조회 (신규)

`ticket-key: booking-v1/operator-status`
**생성 상태:** `open,status:blocked,feature` / Parent: P / Blocked by: F

**목표:** 운영자가 예약 ID로 예약 상태를 조회하고, 일반 회원의 접근은 거부합니다.

**범위:** 운영자 전용 단건 조회 API와 예약 도메인 조회 기능을 구현합니다. 역할 검사와 오류 변환은 F를 재사용합니다.

**판정 순서**
1. 미인증: `AUTH_REQUIRED`, 401
2. 운영자 아님: `AUTH_FORBIDDEN`, 403 (예약 조회 전에 거부)
3. 저장 장애: `BOOKING_STORAGE_UNAVAILABLE`, 503, `retryable=true`
4. 예약 없음: `BOOKING_NOT_FOUND`, 404
5. 성공: 200 `{ "bookingId": "...", "status": "..." }`

오류 코드가 먼저 완료된 C에 이미 있으면 재사용하고, 없으면 같은 이름과 의미로 예약 도메인에 추가합니다. C와 O 사이에 실행 순서 의존은 없습니다.

**제외:** 목록·검색, 상태 변경, 취소, 삭제, 환불, 개인정보 등 추가 필드 노출.

**인수 기준**
- [ ] 운영자는 활성 예약과 취소된 예약 각각의 실제 상태를 받습니다.
- [ ] 일반 회원은 본인 예약이어도 403을 받고, 저장소 조회가 일어나지 않습니다.
- [ ] 미인증 요청은 401을 받습니다.
- [ ] 없는 예약은 404를 받습니다.
- [ ] 저장 장애는 404, 기본 상태, 빈 성공이 아니라 503, `retryable=true`, trace ID로 응답합니다.
- [ ] 조회 전후로 저장된 예약이 변하지 않습니다.
- [ ] 응답에 `bookingId`, `status` 외 필드가 없습니다.

**검증과 완료:** 역할별 use case 테스트, 장애 주입, 실제 API 실행으로 확인합니다. 명령, 결과, 커밋을 기록한 뒤 `status:active`를 제거하고 완료로 닫으며 `feature`는 유지합니다.

## 6. 요구사항 Coverage

| 요구사항 | F | C | O |
|---|---|---|---|
| R1 본인 취소, 24시간 제한, 멱등 성공 | 인증 제공 | **담당** | – |
| R2 운영자 조회, 일반 회원 거부 | 역할 검사 제공 | – | **담당** |
| R3 공통 경계 변환 | **담당** | 재사용 | 재사용 |
| R3 도메인의 오류 의미 소유 | 소유하지 않음 | **취소 오류** | **조회 오류** |
| R4 저장 장애 시 재시도 가능 오류 | `retryable` 변환 | **쓰기·읽기** | **읽기** |
| 제외: 삭제·환불 | 제외 명시 | 제외 명시 + 검증 | 제외 명시 |

## 7. 무결성 검사

| 검사 | 결과 | 근거 |
|---|---|---|
| **누락** | 현재 snapshot 기준 R2 누락, O 생성 후 해소 | 위 표에서 R1~R4 모두 담당 티켓 있음 |
