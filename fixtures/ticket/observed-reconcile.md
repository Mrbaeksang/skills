## 결론

1. `store-v1/buy`는 **게시 상태 미확정**이고 완료가 아니다. 재생성하지 말고 추가 쓰기를 멈춘다.
2. 공통 오류를 선행 티켓 E로 분리해 순환을 없앤다. 그래프는 `E → A′`, `E → B′`, `F → C`이다.
   - **frontier:** `{E, F}`. 단, F는 결함 수정 계약과 수용 기준이 기록된 경우에만 포함되며, 없으면 F는 `status:triage`이고 frontier는 `{E}`이다.
   - **C:** `status:ready`에서 `status:blocked`로 전환한다.

## 1. `store-v1/buy` timeout

**다음 행동**
- create를 반복하지 않는다. 전체 목록의 0건은 최초 요청이 적용되지 않았다는 증거가 아니고, 시간이 지난 것도 재생성 근거가 아니다.
- 이 슬라이스에 대한 관계와 라벨 쓰기를 포함해 추가 쓰기를 중단한다. 대상 이슈가 없으므로 `status:blocked` 라벨을 붙일 수 없어, 기록은 로컬 대응표에 남긴다.
- 기록 항목은 key, marker, 대상 저장소, 요청 시각, timeout 응답, 목록 조회 범위와 완료 시각, 결과 0건이다.
- 이후 허용되는 동작은 읽기 전용 reconcile뿐이다.

**재개 조건**

| 이후 관찰 | 조치 |
|---|---|
| marker 1건, 의도한 내용과 일치 | 기존 URL을 회수하고 본문, marker, 라벨, 대상을 readback |
| marker 1건, 내용 불일치 | 임의로 수정하지 않고 쓰기 중단. 현재 본문을 다시 읽은 뒤 차이를 조정 |
| 여러 건 | 쓰기 중단. 어느 건을 남길지 해결 조건을 기록 |
| 0건, 조회 실패, 불완전한 목록 | 미확정 유지 |
| 최초 요청이 적용되지 않았고 앞으로도 적용되지 않는다는 확정 증거, 또는 원자적 중복 방지 수단 확보 | 이때만 같은 key로 재생성 여부를 판단 |

**완료 상태:** 게시 미완료(`publication unconfirmed`)이다. "생성됨"도 "생성 실패"도 아니다.

## 2. 순환과 F reopen 조정

**실행 단위** (key의 `<spec-key>`와 slice 이름은 예시)

| 단위 | 범위 | 상태 | 비고 |
|---|---|---|---|
| **E** `<spec-key>/common-error` (신규) | R1·R2가 실제로 쓰는 최소 공통 오류 계약과 검증 경계 | `status:ready` | 공통 오류의 단일 소유자 |
| **A′** `<spec-key>/order-create` (A 수정) | 주문 생성 전체 흐름. E의 계약을 소비하며 재구현하지 않음 | `status:blocked` | 공통 오류 범위 제거 |
| **B′** `<spec-key>/order-read` (B 수정) | 주문 조회 전체 흐름. E의 계약을 소비하며 재구현하지 않음 | `status:blocked` | 공통 오류 범위 제거 |
| **F** (reopen) | 공통 인증 결함 수정 | 조건부 `status:ready` | 이전 done 증거 보존. reopen만으로 active가 되지 않음 |
| **C** | 기존 범위 유지 | `status:blocked` | F 대기 |

A와 B는 기존 key를 유지하고, 시간값으로 key를 바꾸지 않는다.

**실제 dependency**
```text
E ──> A′ (R1)
E ──> B′ (R2)
F ──> C
```
- `A blocked-by B`와 `B blocked-by A`는 공통 오류를 두 티켓에 중복으로 넣어 생긴 관계이므로 제거한다.
- A′와 B′는 E가 해소되면 병렬로 실행할 수 있다. B′의 조회 검증은 fixture나 seed 데이터로 수행해, 편의상 A′에 직렬 연결하지 않는다.

**Coverage**

| 요구사항 | 동작 소유 | 공통 계약 소유 | 필요한 검증 |
|---|---|---|---|
| R1 주문 생성 | A′ | E | 생성의 정상/실패/복구 시나리오와 E 오류 계약 준수 (NOTRUN) |
| R2 주문 조회 | B′ | E | 조회의 정상/실패/복구 시나리오와 E 오류 계약 준수 (NOTRUN) |

**Frontier**
- **현재:** `{E, F}` (F 조건은 결론 참고)
- **active:** 없음 (입력에 실제 수행 근거가 없음)
- **E 해소 후:** A′와 B′를 재조회한 뒤 `status:ready`로 전환하면 frontier에 추가
- **F 해소 후:** C를 재평가

**blocked 원인과 재개 조건**

| 이슈 | 원인 | 필요한 조치 | 재개 조건 |
|---|---|---|---|
| **C** | 선행 F가 결함으로 reopen됨 | F의 결함 수정, C와의 관계를 open blocker로 재확인 | F의 필요한 산출물과 수용 기준 증거 충족, C의 blocker와 계약 재조회 후 영향 없거나 반영 완료 → `status:ready` |
| **A′, B′** | E 미해결 | E 완료 | E의 계약 산출물과 검증 증거 충족, 각 이슈 재조회 → `status:ready` |

- F나 E가 닫혔다는 사실만으로는 해소로 보지 않는다.
- F 수정으로 인증 계약이 바뀌면 C의 수용 기준을 먼저 갱신한다.
- F의 다른 직접·간접 의존 이슈도 재조회해 다시 계산한다.

**적용 순서**
1. E를 게시하고 readback한다.
2. A′와 B′에 `blocked-by E`를 추가하고 readback한다.
3. A↔B 관계를 제거하고 readback한다. 제거 사유와 이력은 남긴다.
4. A와 B의 본문을 현재 내용 기준으로 갱신한다.
5. 상태 라벨을 바꾸고, 상태 수가 1개인지와 무관한 라벨이 보존됐는지 확인한다.

A와 B가 아직 로컬 draft이면 tracker 쓰기 없이 초안에만 반영한다.

**Tracker 미지원 시 대체**
- 의존 이슈 본문에 `Blocked by: <URL> — 필요한 산출물/해소 기준`을 적는다.
  - A′, B′: `Blocked by: <E URL> — 공통 오류 계약과 검증 증거`
  - C: `Blocked by: <F URL> — 결함 수정과 수용 기준 증거`
- 선행 이슈에 역참조(`Blocks: <URL>`)를 적고 양방향 참조를 검증한다.
- A↔B 본문 링크는 제거 사유와 함께 이력으로 남긴다.
- 상태 라벨도 지원하지 않으면 기존 vocabulary에 대응시키거나 본문에 상태를 하나만 기록한다.
- 보고에는 native 미지원과 대체 사용을 명시한다. 단순 권한 오류는 미지원으로 처리하지 않는다.
- tracker를 전혀 쓸 수 없으면 로컬 초안과 대응표로 끝내고 "게시 안 됨"으로 표시한다.

## 검증과 남은 문제

- **수행:** `ticket` 스킬의 본문, `execution-contract.md`, `tracker.md`만 읽었고, 위 결과는 입력 snapshot을 기준으로 한 판단이다.
- **NOTRUN:** tracker 조회·쓰기·readback, native 관계 지원 확인, E/A′/B′/C/F 수용 기준 검증. 게시와 파일 변경은 하지 않았고, 대시보드 보고도 파일 변경 금지에 따라 생략했다.
- **입력에 없어 확정하지 않은 사항**
  - F의 현재 라벨과 결함 수정 계약: frontier의 F 포함 여부를 결정한다.
  - A′, B′, E가 인증 F를 소비하는지: 소비한다면 `F → 해당 이슈` 관계를 추가하고, 그 이슈는 F 해소 전까지 blocked이며 E도 해당되면 frontier에서 빠진다.
  - 공통 오류의 구체적 코드와 형식: 명세에서 가져와야 하며, 여기서 임의로 확정하지 않았다.
