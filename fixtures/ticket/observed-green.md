# booking-v1 티켓 및 상태 변경 계획

**결론:** 티켓은 P(컨테이너), F, C, O 네 개로 구성하며, 새로 만들 것은 운영자 조회 O 하나입니다.

- **C:** marker 일치 1건이 확인됐으므로 재생성하지 않고 기존 C를 회수합니다.
- **F 완료 전 frontier:** `∅` (F는 active로 별도 표시)
- **F 완료 후 frontier:** `{C, O}`
- **C 재개 시 frontier:** 남은 작업에 blocker가 없으면 `{C, O}`, 있으면 `{O}` (O가 아직 ready일 때)

## 1. 근거 구분

| 구분 | 내용 |
|---|---|
| 입력 snapshot | P와 F가 있고, F는 `open`, `status:active`, `feature`입니다. C는 `open`, `status:blocked`, `bug`이고 F에 의존합니다. C marker는 `ticket-key: booking-v1/cancel`이며, timeout 후 전체 목록 readback에서 1건이 확인됐습니다. O는 없습니다. |
| 입력에 없어 미확인 | repository, URL, issue number, database ID, P의 라벨, P·F·C 본문 원문, F marker, C의 native sub-issue 및 blocked-by 등록 여부 |
| 실제 수행 | 로컬 skill 문서 2개 읽기뿐입니다. |
| NOTRUN | tracker 조회·쓰기, 구현, 테스트. 대시보드 보고도 파일 변경 금지에 따라 생략했습니다. |

이후의 모든 상태는 **예상 계획**이며 실제 전환 증거가 아닙니다.

## 2. 티켓

P, F, C 본문은 입력에 없어 명세로 재구성한 **대조·실행 기준**입니다. tracker의 기존 본문이 우선이며, 이 텍스트로 덮어쓰지 않습니다.

### P — booking-v1 (기존, 컨테이너)

- **목표:** 회원의 본인 예약 취소와 운영자의 상태 조회를 제공합니다.
- **자식:** F, C, O
- **제외:** 삭제, 환불
- **역할:** containment만 표현합니다. 구현 작업이 아니므로 frontier 계산에서 제외합니다.
- **완료 조건:** 모든 자식이 done이고 R1~R4 검증 증거가 있어야 합니다.
- **이번 계획의 범위:** P의 라벨과 종료 상태는 변경하지 않습니다.

### F — 인증 기반과 공통 API 오류 경계 (기존, active)

**배경·목표:** C와 O가 재사용할 인증과 오류 변환 기반을 하나의 선행 티켓으로 제공합니다.

**요구사항:** R3(변환 부분), R4(오류 표현 부분), R1·R2의 인증 전제

**범위**
- 요청에서 인증된 주체를 만듭니다. 소비자가 주체 ID와 회원/운영자 역할을 읽을 수 있어야 합니다.
- 미인증 요청을 거부합니다.
- 공통 API 경계에서 도메인 오류를 `오류 코드`, `안전한 메시지`, `trace ID`로 변환합니다.
- 소비자가 재시도 가능 오류를 판별할 수 있게 합니다.
- 미분류 예외를 내부 정보 없는 안전한 오류로 변환합니다.

**제외:** 취소 규칙, 운영자 조회 API, 예약 오류 의미 정의, 삭제, 환불

**계약과 불변식**

| 항목 | 내용 |
|---|---|
| 입력 | 요청의 인증 정보, 도메인이 발생시킨 오류 |
| 출력 | 인증 주체, 공통 오류 응답 |
| 소유 | F는 변환 메커니즘만 소유하고, 오류의 의미는 각 도메인이 소유합니다. |
| 금지 | 오류 응답에 stack trace, SQL, 저장소 주소, 토큰을 노출하지 않습니다. |
| 미확정 | 인증 방식, HTTP status, JSON 필드명, 재시도 가능성 표현. 대상 repo의 기존 관례로 F가 확정해 완료 요약에 기록합니다. |

**선행:** 없음

**시나리오**
- **정상:** 유효한 회원과 운영자가 올바른 역할로 식별됩니다.
- **실패:** 미인증 요청이 거부되고, 미분류 예외에서 내부 정보가 노출되지 않습니다.
- **복구:** 재시도 가능으로 분류된 test 오류를 소비자가 판별할 수 있습니다.

**수용 기준**
1. 실제 API 경계의 test route에서 회원과 운영자 역할이 구분됩니다.
2. 미인증 요청은 공통 형식으로 거부되고 trace ID가 있습니다.
3. test 도메인 오류가 코드, 안전한 메시지, trace ID로 변환됩니다.
4. 미분류 예외 응답에 내부 정보가 없습니다.
5. 재시도 가능 오류를 응답만으로 판별할 수 있습니다.
6. 소비자용 계약(주체 조회 방법, 오류 등록 방법, 응답 형식)이 완료 요약에 있습니다.

**검증 환경:** 대상 repo의 manifest와 AGENTS.md에서 실제 test·실행 명령을 확인하고, 명령과 결과를 기록합니다.

### C — 회원 본인 예약 취소 (기존, `<!-- ticket-key: booking-v1/cancel -->`)

**Parent:** P  
**Blocked by:** F — 인증 주체, 공통 오류 변환, 재시도 가능 오류 표현과 해당 검증 증거

**배경·목표:** 회원이 취소 가능 기간 안에 본인 예약을 API로 취소하고, 재요청에도 같은 성공을 받게 합니다.

**요구사항:** R1, R3(취소 오류 의미), R4(취소 저장 장애)

**범위:** 취소 API, 소유권·기간·멱등 규칙, 취소 상태 저장, 취소 도메인 오류 정의

**제외:** 삭제, 환불, 운영자 조회, F 재구현

**입력·출력**
- **입력:** 인증된 회원, 예약 식별자
- **성공 출력:** 취소된 예약의 동일한 성공 응답

**판정 순서**
1. 미인증이면 F 경로로 거부합니다.
2. 예약을 조회합니다. 조회 실패는 재시도 가능 오류입니다.
3. 본인 예약이 아니면 거부합니다. 이 판정은 이미 취소된 예약에도 먼저 적용합니다.
4. 이미 취소됐으면 기간 재판정이나 쓰기 없이 같은 성공을 반환합니다.
5. 취소 가능 기간이 지났으면 거부합니다.
6. 취소 상태를 저장합니다. 저장 실패는 재시도 가능 오류입니다.

**도메인 오류 의미:** 예약 없음, 본인 예약 아님, 취소 가능 기간 경과, 저장 장애(재시도 가능). 코드 문자열은 F 계약에 맞춰 정합니다.

**불변식**
- 취소 쓰기가 확인되기 전에는 성공을 반환하지 않습니다.
- 동시 또는 반복 요청에서도 취소 전이는 한 번만 일어나고 최초 취소 정보를 덮어쓰지 않습니다.
- 예약 레코드를 삭제하지 않고 환불을 유발하지 않습니다.
- 다른 회원의 취소 여부를 응답으로 노출하지 않습니다.

**추정 (명세 미확정)**
- 기준 시각은 예약 시작 시각이고, 정각 24시간 전은 허용합니다. 이 판정은 한 곳에 두고 주입 가능한 시계로 검증합니다.
- 타인 예약의 응답을 거부로 표현할지 미존재로 표현할지는 명세에 없습니다. 어느 쪽이든 취소 상태는 변하지 않아야 하며, 기존 API 관례를 따르고 선택을 기록합니다.

**시나리오**
- **정상:** 기간 안의 본인 예약을 취소합니다.
- **실패:** 타인 예약 또는 기간 경과이면 상태가 변하지 않습니다.
- **복구:** 저장 장애로 재시도 가능 오류를 받은 뒤 다시 요청합니다. 앞선 쓰기가 실제 적용됐든 아니든 재시도는 같은 성공으로 끝납니다.

**수용 기준**
1. 24시간보다 충분히 많이 남은 본인 예약의 취소가 성공하고, 재조회 시 취소 상태입니다.
2. 24시간 미만이면 거부되고 상태가 변하지 않습니다.
3. 경계값 테스트가 추정 규칙(또는 이후 확정된 규칙)과 일치합니다.
4. 재요청 응답이 최초 성공과 같고 최초 취소 정보도 유지됩니다.
5. 기간이 지난 뒤의 재요청도 같은 성공입니다.
6. 타인 예약은 취소 여부와 관계없이 거부됩니다.
7. 저장 장애를 주입하면 성공 응답이 없고, 재시도 가능 오류에 코드, 안전한 메시지, trace ID가 있습니다.
8. 장애 해소 후 재시도가 성공합니다.
9. 삭제나 환불 부작용이 없습니다.

**검증 환경:** 실제 API 경로와 test 저장소, 시계 주입, 저장 장애 주입을 사용합니다.

### O — 운영자 예약 상태 조회 (신규, `<!-- ticket-key: booking-v1/operator-status -->`)

**Parent:** P  
**Blocked by:** F — 역할 식별, 공통 오류 변환, 재시도 가능 오류 표현과 해당 검증 증거

**배경·목표:** 운영자가 API로 예약의 현재 상태를 확인하게 하고, 일반 회원의 사용은 막습니다.

**요구사항:** R2, R3(조회 오류 의미), R4(조회 저장 장애)

**범위:** 운영자 전용 단건 상태 조회 API, 권한 판정, 조회 도메인 오류 정의

**제외:** 상태 변경, 취소 처리, 삭제, 환불, F 재구현

**입력·출력**
- **입력:** 인증된 운영자, 예약 식별자
- **출력:** 예약 식별자와 저장소의 현재 상태

**판정 순서**
1. 미인증이면 F 경로로 거부합니다.
2. 운영자가 아니면 예약 조회 전에 거부합니다.
3. 예약을 조회합니다.
4. 없으면 예약 없음 오류, 저장 장애면 재시도 가능 오류를 반환합니다.

**불변식**
- 읽기 전용입니다.
- 회원 거부 응답에 예약 존재 여부나 상태가 드러나지 않습니다.
- 저장 장애를 빈 결과, 기본 상태, 미존재로 위장하지 않습니다.
- O는 C를 호출하거나 C에 의존하지 않습니다. 취소 전이 코드도 만들지 않으며, 취소 상태는 저장된 값으로만 읽습니다.

**추정 (명세 미확정)**
- 단건 조회로 범위를 잡고, 목록·검색은 포함하지 않습니다.
- 경로와 응답 필드명은 기존 API 관례를 따르고 기록합니다.

**시나리오**
- **정상:** 운영자가 활성 예약과 취소된 예약의 상태를 각각 조회합니다.
- **실패:** 회원은 거부되고, 없는 예약은 도메인 오류를 받습니다.
- **복구:** 저장 장애로 재시도 가능 오류를 받은 뒤 복구 후 재시도하면 정상 조회됩니다.

**수용 기준**
1. 운영자가 seed된 활성 예약과 취소 상태 예약의 상태를 정확히 받습니다.
2. 일반 회원은 본인 예약을 대상으로 해도 거부되고 예약 정보가 응답에 없습니다.
3. 미인증 요청은 공통 형식으로 거부됩니다.
4. 없는 예약은 코드, 안전한 메시지, trace ID를 포함한 오류를 받습니다.
5. 저장 장애 시 성공 응답이 없고 재시도 가능 오류를 받으며, 복구 후 재시도에 성공합니다.
6. 조회 전후 예약 데이터가 같습니다.
7. C가 먼저 완료된 경우 실제 취소 후 O 조회가 취소 상태인지 확인합니다. C가 미완료면 이 항목은 NOTRUN으로 남기고, 나중에 끝나는 C가 같은 검증을 수행합니다.

**검증 환경:** 실제 API 경로, 회원·운영자 test 주체, seed 데이터, 저장 장애 주입을 사용합니다.

## 3. 상태 변경 계획

### 공통 쓰기 규칙

- 쓰기 전에 PR을 제외한 open/closed 목록을 pagination 끝까지 다시 읽습니다. 검색 인덱스의 0건은 부재 증거로 쓰지 않습니다.
- 라벨은 변경 직전에 읽고, 여섯 상태 라벨 중 이전 값만 제거합니다. 전체 라벨 덮어쓰기는 쓰지 않습니다.
- 변경 후 상태 라벨이 정확히 1개인지, `feature`/`bug`가 그대로인지 확인합니다.
- 상태, 종료, 관계 변경은 각각 readback합니다. 응답이 불명확하면 재전송하지 않고 재조회합니다.
- C가 `bug`라는 분류는 무관한 라벨이므로 재분류하지 않습니다.

### 0단계: reconcile과 F 완료 전

| 순서 | 대상 | 작업 |
|---|---|---|
| 1 | C | 재조회 결과 marker 1건, 본문 동일이면 **no-op**으로 기존 URL을 반환합니다. |
| 2 | C | 재조회 결과가 0건, 여러 건, 조회 실패, 불완전 목록이면 게시 상태 미확정으로 **쓰기를 중단**합니다. 시간 경과나 0건만으로 재생성하지 않습니다. |
| 3 | C | sub-issue와 blocked-by 등록 여부를 조회하고, 없는 관계만 추가합니다. |
| 4 | O | marker 0건이 전체 목록으로 확인되면 UTF-8 body-file로 **한 번** 생성합니다. 라벨은 `status:blocked`, `feature`입니다. |
| 5 | O | 생성 응답이 timeout이면 재생성하지 않고 전체 목록으로 reconcile합니다. |
| 6 | O | 본문, marker, 라벨을 readback한 뒤 P sub-issue와 F blocker를 연결합니다. |

| 티켓 | 예상 상태 | 사유 |
|---|---|---|
| F | `open`, `status:active`, `feature` | 진행 중 |
| C | `open`, `status:blocked`, `bug` | F 미완료. 재개 조건은 F 산출물과 검증 증거 |
| O | snapshot에는 없음, 게시 후 `open`, `status:blocked`, `feature` | C와 같음 |

**Frontier: `∅`, active: `{F}`**

### 1단계: F 검증 통과 후

1. F의 수용 기준별 증거를 확인합니다. 닫힘 자체는 해소 증거가 아닙니다.
2. F에 완료 요약을 기록합니다.
3. `status:active`를 제거하고 `status:done`을 추가합니다. `feature`는 유지합니다.
4. F를 completed로 종료하고 readback합니다.
5. C와 O의 blocker, F 증거를 다시 읽습니다. 다른 미해결 blocker가 없을 때만 각각 `status:ready`로 바꿉니다.
6. 전환 readback 후 frontier를 보고합니다. 해소된 관계는 이력으로 보존합니다.

| 티켓 | 예상 상태 |
|---|---|
| F | `closed(completed)`, `status:done`, `feature` |
| C | `open`, `status:ready`, `bug` |
| O | `open`, `status:ready`, `feature` |

**Frontier: `{C, O}`, active: `∅`.** C와 O는 병렬 실행할 수 있습니다. O가 아직 게시되지 않았다면 frontier는 `{C}`이고, O는 부재 상태의 누락 항목으로 보고합니다.

### 2단계: C 구현·검증·완료

O는 이 과정에 영향받지 않으며, 아래 표는 O가 아직 시작되지 않았다고 가정합니다. O가 시작됐다면 O는 active로 옮겨 frontier에서 빠집니다.

| 시점 | C | Frontier | 비고 |
|---|---|---|---|
| 구현 시작 | `open`, `status:active`, `bug` | `{O}` | 실제 작업 시작과 연결합니다. |
| 검증 중 | `open`, `status:active`, `bug` | `{O}` | 검수 대기 라벨은 만들지 않습니다. |
| 증거 충족 후 | `closed(completed)`, `status:done`, `bug` | `{O}` | 완료 요약을 기록합니다. C에 의존하는 노드는 없습니다. |

### 3단계: C 재개

과거 증거를 보존한 채 reopen하고 `status:done`을 제거합니다. 재개 자체는 active의 증거가 아니므로, 남은 계약을 다시 읽어 다음 중 하나로 전환합니다.

| 재평가 결과 | C 상태 | Frontier (O가 ready일 때) |
|---|---|---|
| 남은 범위 명확, blocker 없음 | `open`, `status:ready`, `bug` | `{C, O}` |
| 새 의존성, 권한 부족, 중요 미결정 | `open`, `status:blocked`, `bug` (원인·재개 조건 기록) | `{O}` |
| 재개 후 실제 작업 시작 | `open`, `status:active`, `bug` | `{O}` |
| 원인이 F 계약 결함 | F를 reopen하고 F 상태도 재평가합니다. C는 `status:blocked`입니다. | O에 영향이 있으면 O도 blocked가 되어 frontier에서 제외됩니다. |

## 4. 관계 처리

| 관계 | 의미 | 대상 | 호출 |
|---|---|---|---|
| Sub-issue | 소속 | P ⊃ F, C, O | `POST /repos/{owner}/{repo}/issues/{P_number}/sub_issues`, body `sub_issue_id`=자식 **database ID** |
| Blocked-by | 실행 선행 | C→F, O→F | `POST /repos/{owner}/{repo}/issues/{dependent_number}/dependencies/blocked_by`, body `issue_id`=F **database ID** |

- 추가 전에 목록을 조회해 중복을 피하고, 추가 후에는 양쪽 이슈와 관계 목록을 readback합니다.
- 자식이 다른 parent에 속해 있거나 기존의 다른 blocker가 있으면 임의로 제거하지 않고, 충돌로 보고합니다.
- 실행 시점에 공식 API 지원과 권한을 다시 확인합니다.
- 본문 링크만으로는 native 관계 완료를 주장하지 않습니다.

**미지원 tracker 대체:** 본문에 다음 형식으로 적고 양방향 참조를 검증하며, native 미지원과 대체 사용을 보고합니다. 단순 권한 오류는 미지원이 아니라 권한 blocker로 보고합니다.

```text
Parent: <P URL>
Blocked by: <F URL> — 인증 주체, 공통 오류 변환, 재시도 가능 오류 표현과 검증 증거
```

## 7. 완료 보고

- **결과:** 티켓 4개와 단계별 상태 계획을 답변으로 작성했습니다. 게시, 구현, 파일 변경은 없습니다.
- **수행한 검증:** coverage와 그래프 검사는 이 답변의 티켓과 snapshot을 대상으로 한 문서 수준 검사입니다.
- **NOTRUN:** tracker readback, 쓰기, native 관계 등록, 상태 전환, 코드 테스트
- **남은 문제:**
  - C의 native 관계 등록 여부는 실제 조회가 필요합니다.
  - 기준 시각과 정각 24시간 처리는 추정이므로, 제품 결정이 다르면 C의 판정과 경계 테스트를 수정해야 합니다.
  - F의 실제 본문이 F 수용 기준을 담고 있는지 확인이 필요합니다. 빠진 계약이 있으면 F 완료 전에 해소해야 C와 O를 ready로 바꿀 수 있습니다.
